# Redbook isolated test prerequisites

Run `node scripts/redbook-isolated/prepare-client.cjs` from `apps/server` to generate a schema-matched client in a new exclusive `.redbook-isolated/run-*` directory; it prints JSON with `run` and `tsconfig`. Set `REDBOOK_TEST_RUN` to the printed `run` for every isolated Jest and process harness invocation. The generator never overwrites an existing run; it uses a synthetic database URL, forbids JS socket/HTTP calls, and disables Prisma auto-install. Local Prisma and its engine must already be installed. The directory is test output, not a production client or database. Network guards do not establish operating-system-wide isolation.

Run `pnpm exec tsc -p <printed-tsconfig> --incremental false` for candidate production-source type checking. The static `tsconfig.redbook-isolated.json` intentionally fails closed: it must not silently select the shared default Prisma client. Run the isolated Jest configuration with the desired test file, for example `pnpm exec jest --config jest.redbook-isolated.cjs xhs-p0-redbook.spec.ts --runInBand`. Missing or invalid `REDBOOK_TEST_RUN` fails closed. The isolated config disables ts-jest diagnostics; the separate type check does not cover test types.

`test/redbook-isolated/xhs-p0-process-exit.worker.ts` is a subprocess worker excluded by the project's default Jest and production build; only the isolated configuration collects it. Run `node scripts/redbook-isolated/xhs-scheduled-process-exit-portable.cjs` to execute the full worker sequence; it creates fresh temporary SQLite files and retains them. It does not listen on ports or access a live source.

Fixture migration and inspection use the same schema-matched Prisma client as the tests, avoiding `node:sqlite`; the actual fault occurs inside the unchanged worker's Prisma transaction. On 2026-11-04, an isolated Windows run using Node 20.9.0 and Prisma CLI/client 5.22.0 passed five targeted suites (40 tests) and this complete seven-child process-exit sequence. These are synthetic SQLite/source tests, not a live collection or physical power-loss acceptance. The Jest config transpiles TypeScript files individually; diagnostics are disabled and production type checking remains a separate check. The older `xhs-scheduled-process-exit.cjs` remains as a Node 24 comparison harness.
