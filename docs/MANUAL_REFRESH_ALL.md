# 手动全部更新

主页“更新全部”通过本机鉴权后的 `feed.beginRefreshAll()` 接收请求，立即返回持久批次 ID、目标数量、待发送数量、跳过数量和是否复用原批次。页面持续查询 `feed.manualRefreshBatches()`，分别显示排队、上游受理和缓存同步数量，以及逐号原因。关闭页面不会取消后台处理；重新打开仍能查看原批次。

本轮目标为启用、绑定微信中转来源的现有订阅；停用和其他来源计入明确的跳过数量。一次最多 1000 个目标。新请求复用已有 `Wechat2RssSubscriptionBatches` 的存储和串行调度，无新增依赖或第二套队列。普通新增订阅批次保留原投影与进度；默认普通批次查询不混入手动更新批次。

每个目标通过现有 provider 的 `/add/:id` 提交更新，先检查原账号状态，再核验一致性备份、原子预留既有 15 分钟的逐号冷却字段；共享调度中手动提交至少间隔 30 秒。账号受限、需要官方验证、来源变化或冷却阻塞会暂停批次。不会登录、换账号或绕过限制。缓存等待期间可继续受理后续目标。

提交前先持久写入 `submitting`。回执未知、超时或进程在提交时中断，恢复后明确暂停，不重发 `/add`。只有已确认受理的目标允许“继续检查缓存”，仍只读缓存。停止取消尚未发出的目标，已发出的请求无法撤回；确认受理的目标仍可在同一调度中完成缓存同步。缓存最多检查十次、每次至少间隔 30 秒，仍不就绪会暂停。

上游受理不证明最新文章已经生成。页面“缓存已同步”只表示本轮已经读取并存储现有缓存正文；图片完整性另有实际标记，不冒称全历史或最新文章覆盖。已有数据仍经原备份及非空保护路径保存。

旧单号 `feed.refreshArticles({mpId})`、旧批量同步接口及定时任务的默认缓存消费行为不变。旧批量同步仍运行时，新手动提交拒绝受理并解释原因。旧接口的内存互斥锁移至首次异步读取之前，避免同时调用重叠。

## 完成此前点击的一次请求

管理员可在本机鉴权入口传 `feed.beginRefreshAll({feedIds, intentKey})`，冻结为先前点击时已有的订阅集合，`intentKey` 为该原请求证据的固定 64 位小写十六进制摘要。此意图写入原批次持久记录；即使已完成、停止、重启或订阅集合变化，相同意图仍返回原批次，不再提交。页面后续新的明确点击默认不带此恢复标识，代表新请求，仍受冷却保护。

部署前只做离线回归，不用生产按钮重复测试；部署后先确认旧批量接口 `running=false`、核验备份及既有手动批次，再接收这一次原请求，立即保存返回的 `batchId`，后续仅查询。重复点击进行中的批次会复用原记录。请求结果未知时先查询持久记录，不重新发送；未知提交项也不会因恢复原意图而再次发送。

当前回归覆盖原普通批次、同批重复受理、串行间隔、缓存等待与后续受理、未知提交和重启、停止在飞、缓存检查上限、来源及账号限制、原子冷却预留、本机 UI 的即时回执和恢复进度。Mock 和类型检查不代表真实上游更新成功；实际受理、最新文章及文件保存由统一发布后的单次验收分别记录。
