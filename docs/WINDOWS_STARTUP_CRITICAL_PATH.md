## 有依据的冷启动改动

旧流程在开启 Node SQLite 准备前，同步等待一次只读端口检查完成。新流程使用同一已校验 C# helper 异步读取端口，与原来的完整数据库准备并行；**两者全部结束并通过后**才允许继续。任一失败都拒绝启动，不遗留后台准备任务。原有启动前最后一次端口检查、完整进程 Snapshot、精确 Stop 和整包校验保留。没有检查被删掉，也没有放宽任意 PID。

数据库准备仍包含固定版本 SQLite 的只读一致事务、完整迁移/列检查、全部受保护字段基线、新建一致性备份、独立副本的类型和值比对、备份 SHA 和源 DB/WAL 身份复核。检测到占用端口时，可能多留一份已经完成核验的备份，但不会运行应用或写入源数据库。旧 Python 准备路径及 helper 缺失/强制 PowerShell 时的原检查路径保留，未降低 ExecutionPolicy。

同一复制包的原型平衡六次对照，controller 中位数 **2.877→2.705 秒**；新方案单次为 2.699、2.705、2.917 秒，一次对照反向波动。正式源码对照进一步统一根目录、身份 helper 和 receipt 缓存，仅从原提交读取旧 controller 在内存执行作对照，顺序仍为旧、新、新、旧、旧、新：

| Controller 总耗时，秒 | 旧流程 | 新流程 |
| --------------------- | -----: | -----: |
| 第一个邻近配对        |  2.781 |  2.650 |
| 第二个邻近配对        |  2.955 |  2.685 |
| 第三个邻近配对        |  3.369 |  3.163 |
| 中位数                |  2.955 |  2.685 |

三个配对分别节省 0.131、0.270、0.206 秒。独立 baseline 根目录得到的更大差值仅用于排查，不作为收益依据。新流程仍有一轮超过三秒，稳定三秒或点击到页面的三秒目标没有因此成立。
