# 可靠本地应用交付

## 工作顺序

1. 明确用户目标、受影响的数据和环境、可执行权限、验收条件与停止条件。遵从用户对平台账号、自动化和访问方式的明确限制；不要把后台 HTTP 当作天然安全，不设计绕过限制的流程。
2. 锁定准确代码 SHA、运行版本与数据结构；分开记录“代码已修复、测试已通过、已部署、用户路径已验收”。先查已有证据，不把旧结论套到新版本。
3. 按风险阅读 [数据与恢复检查单](references/data-and-recovery.md) 或 [交互与交付检查单](references/delivery-checklist.md)。只做能关闭当前风险的最小改动；优先事务、唯一约束和清晰状态机，不用无限增加安全工具代替交付。
4. 把真实失败化为脱敏、合成、可重复的回归场景。按列表、正文、图片、归档分别验收，并覆盖中断、重启、并发和部分成功。仅在获授权环境执行测试；不接触生产数据来证明设计，不创建自动删除脚本。
5. 按阶段测性能并保留可比基线。诊断启动、退出和健康检查时绑定进程、时间、版本及日志；证据不足就保留“未知”。
6. 在获授权范围内执行最小发布并准备回退；核实部署 SHA 与实际用户路径。多窗口开发隔离工作区、端口和状态；生产保持单写者。
7. 交付短报告：目标与准确 SHA、已完成项、测试证据、部署和验收状态、未解决风险、下一步。交接非敏感代码、测试和产品/技术文档；排除凭证、私人数据和本机审计。历史案例仅用于解释方法，见 [案例与证据边界](references/cases.md)。

## 证据纪律

- 用请求、来源和对象身份解释成功；HTTP 200、缓存成功、单个子任务成功均不等于整个任务完成。
- 遇到不明回执，先核查持久证据和远端状态，不盲目重发；缺失证据不能编造为成功或失败。
- 对关键修复锁定 SHA 独立复核，保留失败反例和修复后的结果。测试数量是证据索引，不代替覆盖证明。
- 承认边界：未部署不能称生产解决；一个仍未知的历史请求不能因新恢复机制通过测试就改成已解决。
