# Preserving restart: fixed runtime and process families

The preserving installer can opt into `preservingUpdate.processFamily: { format: 1 }`. This is an installer contract, not a change to collection permissions or application behavior.

- A reviewed launcher with `pointerPath` continues to follow the active pointer. An exact runtime invocation instead uses `packageId`, never both fields. Its complete argv, executable pin, package-local entry pin and working-directory contract remain mandatory. Explicit database paths outside package roots are accepted only through that exact invocation; roots are not widened.
- Each package declares one root invocation and its enabled helper invocations. A helper's `parentEntry` identifies the root entry. Admission verifies full process identity, parent PID, invocation binding and creation-time order. An older orphan cannot attach to a reused parent PID.
- Optional `processFamily.consoleHost` pins the actual System32 console executable, its file identity and complete two-token argv. A verified root or helper can have zero or one such console child. Console descendants remain part of the family and cannot have further descendants. Other executables, arguments, duplicate hosts and changed identities are rejected.
- Startup binds the owned root immediately, then admits only previously absent reviewed members until the complete reviewed family is ready to seal. Existing members cannot disappear or change PID/start/argv during admission. After sealing, the set is fixed. Candidate and fallback invocations remain bound to their own package even before the active pointer changes.
- A confirmed root stop starts a bounded observation period for the frozen family. Helpers and consoles must all exit before backup or fallback. A child disappearing between the two native samples carries its complete earlier identity; both samples are checked for unknown members and PID reuse. No generic incomplete-query retry or tree-kill receipt substitutes for exit evidence.

HTTP readiness is not helper readiness: `main.ts` listens before `startSnapshotsAfterStartupAudit`, and the snapshot guard then awaits local filesystem checks before spawning. The cache monitor also performs async filesystem checks. Preserving restart completes its backup before spawn and does not use background startup preparation, so the family wait is for these local startup steps, not an indefinite audit or a source request. After HTTP readiness, candidate and fallback have a 15-second retry budget for a required ordinary helper that has not yet appeared. This is a bounded allowance, not a claimed application startup guarantee. Each original synchronous reference query retains its own 30-second timeout, so the retry budget is not a 15-second total wall-clock bound. No further query starts once that budget expires.

Only a successful complete query whose existing members all pass strict identity checks can report that absence. Unknown processes, incomplete queries, duplicates, exited/replaced members and PID reuse still fail immediately. The old family must be complete before stopping, without this wait. Consoles remain optional zero-or-one at admission and fixed after seal. A candidate timeout uses the existing exact owned-root cleanup; fallback is permitted only after the entire admitted family is independently proven exited. Unknown or changed cleanup observations still block fallback.

The frozen runtime artifact from source commit `8fb806a54d415fc779881cee93fe7f3035dec385` can remain unchanged for this installer-only repair. The changed installer modules are outside its runtime copy/bundle closure. The broader `build.cjs` source fingerprint does include installer scripts, so a new build fingerprint would change. Record the original application artifact/manifest identity and the new installer-tool commit separately; do not label the existing application as rebuilt from the tool commit.

Verification covers fixed old/candidate/fallback mappings, staggered family startup and exit, console ownership, rejected unknown/reused identities, and a real isolated Windows Node/Python/console family using the original identity tools and reference resolver. These tests do not establish production installation or source-collection recovery. Production still requires reviewed frozen policy/caller inputs, current identity evidence, existing backup limits and successful CI.

Historical deployed-source regression pins remain unchanged. A test-only inverse records the exact seven reviewed restart hunks from the installer-family commit back to its predecessor, checks both complete source hashes, and then applies the original compatibility and admission checks. Changed new family guards or unrelated old writer gates are rejected; this inverse is not used by installation or runtime code.

## Reviewed empty install-claim recovery

An interrupted install that exhausted the whole-operation scan timer can leave a claim even when no output was registered or created. Ordinary `open` still refuses it. The existing `bindingRepairFile` and `bindingRepairSha256` options now accept one additional explicit receipt kind, `interrupted-empty-install-claim-recovery`, for this narrow case. It does not recover unknown output, change restart policies, reset history, or assert that the failed install succeeded.

The format-1 receipt binds the scope and registry identity, old policy path/hash, new policy hash, original ledger bytes/hash/payload digest/file identity, adoption sentinel hash, exact `claimId` and `claimSha256`, reviewed source identity and review evidence. It also binds `failureCode: RELEASE_SCOPE_SCAN_TIME_BUDGET`, `failureEvidencePath` and `failureEvidenceSha256`. The original ledger must have no previous binding repair, no outputs, and an install claim with no outputs whose root/reservation/runtime count match the new request. All exclusive output allocations must remain absent.

Only two policy changes are admitted:

- Add an explicit `scanBudget` with profile `legacy-stream-v1`, checkpoint mode `full`, `scanEntries: 100000`, `operationEntries: 1000000`, `scanReadBytes: 1073741824`, `operationReadBytes: 2147483648`, and `durationMs: 300000`. The old policy must omit `scanBudget`. This retains every small-profile non-time limit; scanner defaults and restart budgets are unchanged.
- Replace the SHA of the unique existing launcher file pin for the executing `release-scope.cjs`. `toolBinding` supplies its exact path and old/new hashes. `allowedDifferences` must list `scanBudget`, then the exact `windowsReferences.launchers.<index>.files.<index>.sha256` leaf. Reversing those changes must reproduce the original complete policy. Probe, other files, argv, launchers, roots, allocations and runtime limits cannot change.

The original installer creates its build lock before opening the scope. That control is excluded from the history digest but charged in the claim's start bytes. `releasedBuildLock` binds the unchanged fixed sibling `install-lifecycle.cjs` SHA and an integer `ownerPidDigits` from 1 through 10. The exact UTF-8 size of the existing `{pid, token: UUID}` serializer must explain the entire difference between the original start bytes and baseline bytes. Historical writer provenance must be checked against the archived caller/tool pins when reviewing the receipt. This is an explicitly reviewed accounting explanation, not reconstruction of the former PID or token. Current measured bytes must equal the frozen baseline exactly and both build and active locks must be absent.

Recovery uses the original registry lock, validates protected artifacts and the full effect baseline, and performs complete reference checks before the snapshot and before commit. Only a validated task/shortcut's exact approved `viaPointer.launcherSha256` is inversely mapped to the old launcher-files hash for comparison with the original claim's reference digest. All other facts remain exact. Local identity, baseline, lock, evidence and allocation checks repeat after each potentially slow query; the ledger commit also compares original bytes and identity.

The immutable snapshot contains the original failed ledger, old/new policies, approval and failure evidence bytes. Only then can the atomic ledger update clear that exact old claim, bind the new policy and append the recovery receipt. The adoption sentinel, unknown extra ledger fields and original failure remain intact. An exact committed recovery can be replayed; a newly interrupted claim, partial/tampered snapshot or any output cannot reuse that receipt. If an atomic write has an uncertain outcome and ownership cannot be re-established, the scope lock stays held for review. Never clear it or retry automatically.

Call `scope.open` explicitly while the install locks are absent, then pass the returned lease to the unchanged `installPair(..., { scope: lease })`. Do not call the internal-open route, open a second scope or close/reopen between these steps. The installer owns its usual close once it has accepted the lease; if it fails before acceptance, the caller must preserve the original error and attempt the lease's guarded close once. A failed close is a review boundary, not permission to repeat the install.

The one-candidate recovery plus normal install path uses two recovery reference calls and seven existing install calls. The 300-second whole-verifier budget allows nine 30-second outer query limits plus 30 seconds of local work; the inner native collector remains bounded at 20 seconds. This is finite headroom, not a promise of completion. Extra full checks still count against the unchanged entry/read limits. Synthetic tests cover the original timer failure with a real transient lock, exact history preservation, normal installer continuation, concurrency, late mutations, replay and fail-closed counterexamples. They do not establish production installation or collection recovery.
