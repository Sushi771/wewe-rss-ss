# 空间防护集成与上线前检查

> **有限默认已落实（2026-10-13）：** 32 GiB / 48 库 / 生成后余 4 GiB；测试为 512 MiB / 12 库 / 余 256 MiB。历史总量已超限，候选不得直接激活；具体恢复窗口和历史归档仍需明确决定。见 [预算决策说明](SPACE_GUARD_BUDGET_DECISION.md)。

候选基于 `edb0ecb799852a37bd26b7879a7962b10fbd98f3`，在独立 E 盘 worktree 中实现，不包含 redbook 候选，不修改生产目录的用户脏文件。本候选不等于已经部署：只有重新构建、独立验收、审查并交接后，生产运行时才可能使用防护。

## 统一入口与迁移边界

采集写前备份、周期 `SqliteSnapshotGuard`、受控启动/重启/切换和后台启动审计统一使用 `SQLITE_PRODUCTION_BACKUP_ROOT`，默认仍为数据库同目录的 `backups`。没有悄悄新增 `full-snapshots` 根来绕过历史总量。预算和 `.space-budget.lock` 在同一规范化根上共享，按所有现有文件/恢复点计算。测试另用聚合测试根；外层演练租约 `.test-run.lock` 与逐个复制的 `.space-budget.lock` 分开，避免子进程避开配额或锁死自己。

配置必须是绝对路径。换配置只改变未来生成目标，不迁移、不删除原历史恢复点；换盘和旧恢复窗口须人工核对。`SQLITE_TEST_BACKUP_ROOT` 只在显式 test 策略下生效，不会把生产备份带入测试根。

现有生产布局包含从 E 盘备份根指向 C 盘 `backups-legacy-20261012` 的 junction。它们不能被默默当作普通目录或完全忽略。需要明确的 **只读迁移白名单** `SQLITE_PRODUCTION_LEGACY_ROOTS`（JSON 绝对路径数组）。仅允许遍历指定根内的历史目标并将其容量计入统一预算；拒绝未列出的链接、重复目录和循环。白名单不授权任何历史删除或改写。测试策略始终拒绝这类链接。

上线前须先为已核实的 legacy 根配置白名单，再运行只读预检；没有白名单时当前布局会明确报告 `SQLITE_BACKUP_LAYOUT_REQUIRES_REVIEW`，不可直接推进上线。配置应通过正式部署环境持久化，不能只设置在一次终端会话中。

```powershell
# 在隔离验收中试算；实际配置路径须由操作者核实
$env:SQLITE_PRODUCTION_LEGACY_ROOTS = '["C:/path/to/project/apps/server/data/backups-legacy-20261012"]'
python apps/server/scripts/backup-space-status.py --database C:/path/to/project/apps/server/data/wewe-rss.db --backup-root E:/CodexTemp/wewe-runtime-backups --archive-plan
```

这个命令只读取文件元数据和小验证 receipt，不生成生产副本、不哈希整个生产库、不删文件。输出含私有路径，放私有验收目录，不提交 GitHub。归档候选仍需重新核验哈希，清单不是删除授权。

## 生产默认预算与当前实测

初次收口时历史恢复点已超过建议预算。后续由获授权的独立清理窗口处理部分历史点；本窗口仅重新只读核验。清理后统一逻辑根（包括显式认可的 C 盘 legacy 目标）字节占用已低于 32 GiB，但 SQLite 数量仍超过 48；不能把 E 盘物理占用与跨根逻辑计数混为一谈，也不能豁免 legacy 来通过检查。实际私有路径、清单和容量结果只保留在本地证据。

修正后的有限生产默认值：**48 个 SQLite、32 GiB 总文件、生成后至少 4 GiB 空闲**。测试默认仍为 **12 个 SQLite、512 MiB、至少 256 MiB 空闲**。任何一项先到阈值就拒绝生成；配置必须为有限正整数。Node 入口、Python 备份和只读工具采用同样默认，legacy 历史点全部计入。

当前历史总量已经超过默认字节与数量限制，下一份备份保守预留约 **1,430,757,376 字节**，新生成应被拒绝。约 715 MB 源库每 15 分钟持续变化最坏每天增加约 **68.6 GB**；32 GiB 预算本身不能永久维持原备份保障。可靠去重只减少未变化时的重复副本，不降低必要备份频率。

达到 50% 字节或数量使用率，或按每 15 分钟持续变化预测剩余不足 24 小时，提前提示。预算状态经现有 `/startup-status` 和顶部提示展示。预算耗尽时提示新恢复点暂停、历史点保留及人工归档；启动审计因预算失败仍保持缓存阅读可用，保护写入不放行。容量预测是连续变化情景，不是实际增长保证。

## 可执行维护规则：保留恢复点，人工批准归档

1. 每天运行只读 `backup-space-status.py --archive-plan`；出现容量预警时立即运行。将失败半成品、最新可信点、历史时间范围及可回收空间一起审阅。
2. 待用户确认的较小活跃窗口为近三小时全部 15 分钟点、近 12 小时每小时点、近三天每日点及版本/迁移边界点，非重叠时约 27 份、19.3 GB。这个选择仅决定哪些点值得优先保持可直接打开，**不自动删除其他唯一点**。脚本列出的旧点也只是供人工检查的归档候选，并排除每个已识别源的最新点。
3. 对另外明确批准的清单，采用可逆的无损压缩/冷存储：先生成压缩档，流式解压校验 SHA-256 与原文件完全一致，核验恢复步骤，再决定是否批准移除重复的未压缩文件。旧唯一恢复点始终有完整可恢复副本；当前 guard/最新 receipt 正在引用的点不得移动。
4. 归档存储也需要明确的有限容量、目录和负责人；放在同一个盘只改变活跃根配额，不会增加整盘空闲。应压缩到经过验证的容量或存入经过批准的独立存储。需要永久淘汰哪些历史恢复点必须另获具体授权。
5. 没有归档空间或未获处置授权时，提前报告并在硬阈值前停止新的受保护生成。不能通过静默删旧点或取消必要备份让操作继续。

本候选没有后台永久删除、自动历史压缩/移动或定期清理动作。上面维护步骤需要明确操作者执行和批准，不会因为过去批准过一批删除而自动扩大授权。

## 复用的安全证据

文件 `dev/ino/size/mtime/ctime` 相同绝不授权跳过备份。Python 和 Node 每次复用都在独立 SQLite 一致读事务中比较全部 schema 对象和各表的完整 typed rows，再核验旧恢复点 SHA-256、完整性与源归属。SQLite 读视图包含已提交 WAL 内容，避免 Windows 持久写句柄时间戳延迟导致错复用。内容变化即使元数据被冻结也必须新建并校验恢复点；冻结元数据的 DB/WAL 回归覆盖这一点。

周期守卫建立新可信代际仍要求新恢复点，原有 lease、字段保全、schema 验证和写入保护没有为省空间放宽。新恢复点源变化检查还会比较独立当前读视图，不能仅依赖 Windows 文件时间戳。
