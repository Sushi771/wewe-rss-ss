Each run creates an exclusive fresh audit directory, nonce-bound root owner lock and `run-manifest.json` **before** starting SQLite generation. The original source is outside the fresh audit and is never registered for cleanup. A successful `begin()` records synthetic file identity. `checkpoint()` records additional disposable SQLite files in this owned audit directory; adapters should call it after creating copies and before long async work. Kept evidence has no automatic expiry or historical deletion policy: reaching quota blocks further generation for manual review.

If the owner is forcibly killed, no in-process helper can guarantee its `finally` runs. After stopping and verifying **only that run's** known children, use the explicit recovery tool:


Recovery never kills a process. It refuses an active/reused PID, mismatched token or manifest, changed audit/file identity, links or an outside path. ## Release package lifetime and existing installations

**The three-role checks below are supplemental. They do not exempt any historical byte from the shared scope described here. Production adoption remains blocked until the shared policy and its authoritative reference probe are independently reviewed.**

`release-scope.cjs` is the common accounting/nonce-lock layer used by generation, installation, production switch/restart, and explicit activation. Every cooperating window must receive the same private `WEWE_RELEASE_SCOPE_FILE` and pinned `WEWE_RELEASE_SCOPE_SHA256` in that invocation's environment. It is not a global environment change. The reviewed registry resides outside its existing accounting roots and contains canonical paths, filesystem identities, an immutable complete inventory digest/byte/runtime-copy baseline, an absolute `maxBytes`, finite `maxGrowthBytes` (at most 768 MiB), and `maxNewRuntimeCopies` (at most four, including source/destination transient duplicates). The installed-role limit remains three; a frozen source plus its installed copy both consume total capacity. Worktrees, failed outputs, caches, bundles, historical and unclassified files are included across all registered roots. Unknown/unregistered roots, overlaps, hardlinks and escaping aliases fail closed. Canonical root identity prevents case/junction aliases from getting an independent allowance. Use the same reviewed registry; creating another registry to evade its reservation is outside the authorized protocol.

The default absolute limit remains 768 MiB. An existing over-limit root is **not** automatically grandfathered. A finite compatibility exception requires a separately approved immutable policy containing `exception.approvalId`, the exact baseline digest/bytes, exact absolute ceiling and growth ceiling. Naming old directories `legacy` is not such approval. The exception never expands on retry, and every historical file's content/identity/size and every unknown/cache entry remain frozen. New/grown/replaced history stops the next allocation. The default small scan remains 100,000 entries / 30 seconds. The explicit streaming legacy profile below adds separate per-pass and whole-operation budgets; any incomplete pass still stops and no partial inventory is accepted. Logical bytes and runtime counts are measured across all roots; the actual volume free-space reserve is enforced separately before peak reservation and at checkpoints. Internal aliases are recorded without charging the same stored files twice. Three direct root control files (`active.json`, `.build-budget.lock`, `.release-lifecycle.json`) may change under their own pointer/owner protocol, remain byte-accounted and are individually limited to 64 KiB.

The shared state records a durable nonce-bound intent **before** mkdir/copy, then directory identity before bulk output. Source bytes already exist in the baseline; all new copies, compilation/dependencies, temporary files and logs consume the requested transient reservation. All registered roots contend on the same registry lock, including across async controller waits. New paths are recorded before creation and verified completed outputs remain charged. Failed owned output is eligible for local cleanup only after a complete fresh reference query proves it inactive; changed ownership/identity, uncertain child exit, a killed owner, partial output, changed references or a missing/replaced/corrupt adopted ledger hold the claim. No new timestamp is allowed over that unresolved claim. There is no automatic stale-lock recovery or historical retirement in this version. Even manually removing a completed held output does not release its capacity: a separately reviewed registry transition is required. This conservative boundary intentionally stops a later release rather than losing provenance.

The production owner must provide a read-only reference probe whose file SHA is pinned in `policy.probe`. It is invoked freshly before allocation/publication and cleanup, with a 30-second timeout and 1 MiB output limit. Its JSON contract requires `complete:true`, explicit success for `processes`, `tasks`, `shortcuts`, `pointers`, `rollback`, `inflight`, no query errors or uncertain children, and records resolving each reference to a registered physical package with stable identity. Process records additionally require PID, start identity and executable SHA. Stable launcher/task/shortcut arguments must be traced through their active pointer by that probe; an unresolvable reference must be returned as an error. References outside the at-most-three approved protected IDs stop admission. The probe must also return the independently verified additive-schema/unknown-state compatibility proof SHA and `businessDatabaseRestored:false`; a generic manifest label is insufficient. A missing probe or incomplete query holds output. The read-only Windows adapter and its collector are supplied in [Windows reference probe](WINDOWS_RELEASE_REFERENCE_PROBE.md), including exact launcher-dependency/rollback/compatibility policy requirements. It remains a trusted independently reviewed adapter: native production discovery has not been executed or implicitly approved by synthetic tests. `policy.packageProofs` pins each activation package's full manifest SHA. Tasks/shortcuts/rollback/in-flight references must remain unchanged across switching; only planned protected process/pointer transitions are allowed. The already-verified active package's routine logon reuse keeps its existing startup path, so release-capacity exhaustion does not block ordinary subscriptions or routine startup.

The offline scope tests exercise the L1-L12 refusal boundaries, including a real owned inert-child hard kill. They do not establish full operational acceptance of historical retirement, registry amendment, Windows reference discovery or a real production switch/rollback. Those remain explicit review boundaries. ### Publication cache and recovery boundary

Observation is not publication authority. Every host write/controller entry rejects a `reference-inspection` session before file/process work. Pointer publication requires an existing `activate`, `restart` or `switch` claim, at least 4,096 reserved bytes and the exact claimed installed root; protected-package verification alone grants no write capability. Output creation/cleanup and owned-audit writes also require a writer claim with nonzero reservation. A nested operation must retain the same kind, canonical root and pinned policy, cannot increase reserved bytes/runtime copies or gain transition permission, and cannot open a second lease. Reusing an equal-length pointer does not bypass these checks. The three independent observation/publication counterexamples and sync/async/all-entry regressions exercise refusal before mutation.

A shared publication lease retains full package verification instead of seeding the historical `.verification-cache`; controlled children receive receipt reuse disabled. A missing native identity-tool cache uses the existing guarded PowerShell implementation instead of compiling into frozen history. Full 20-item RSS acceptance still runs, and its receipt is written only beneath the fresh identity-checked audit directory already reserved by that operation. Arbitrary receipt roots and junction escapes are refused. Existing caches are still inventoried; cache growth is not exempted. Ordinary startup outside a release lease keeps its existing behavior. It can require fresh review of subsequent cache changes before a later release; this is a conservative hold, not a silent baseline increase.

Both synchronous and asynchronous publication honor the explicitly planned pointer-transition contract. If allocation/inventory verification fails after stopping the old service, the restart/switch fallback may authorize **only** the already existing rollback package bound by the pinned additive-schema/unknown-claim acceptance proof, with matching ID, source commit and full manifest SHA. It still fully verifies package bytes and retains the original process/port ownership and readiness checks. This recovery authorization does not grant output creation, copies, database restoration, budget reset, history retirement or release of the failed claim; a different/tampered/unproven target is refused. The scope owner/policy identities must still match. A zero-allocation observation context cannot request recovery publication. Allocation failure remains reported/held after the compatible service is restored. ### Segmented streaming historical verification

`scope-inventory.cjs` replaces the whole-tree row table with incrementally framed SHA-256 content and metadata receipts. It streams directory entries via `opendir`, retains at most 4,096 sorted names per directory and a globally charged 32,768 names / 16 MiB name buffer, permits depth at most 128 and 64 KiB encoded paths, and reuses one 64 KiB content-read buffer. Directory handles close before descending. Every 2,048 receipt records complete a segment; only aggregate segment count/root and running hashes remain, not millions of file rows or large spool files. No sampling or historical-path exemption is used. A changed directory during enumeration/descent, escaping link, hardlink, memory limit, read limit, entry limit or deadline produces an explicit hold.

The reviewed policy may select `scanBudget: { "profile": "legacy-stream-v1", "checkpointMode": "identity-times-v1" }`. Its fixed ceilings are 1,500,000 visited entries and 32 GiB content reads per pass, **16,000,000 total visited entries / 64 GiB total content reads / 30 minutes across the entire operation**. Numeric overrides may only tighten these limits; inherited/unknown/unlimited profile names are rejected. This is a verification resource budget, not a storage-budget exception. Repeated passes cannot reset it. The small profile and all storage/Node-copy/free-space bounds stay unchanged.

Full content hashing is the default at every checkpoint. The explicitly reviewed `identity-times-v1` mode first rehashes every frozen historical file at the beginning of each operation. Subsequent checkpoints in that same nonce-held operation still enumerate **every** historical member and validate filesystem identity, size, ctime/mtime and complete directory membership against that full receipt; they do not reread unchanged contents. Completed owned outputs get the same full-first/metadata-later treatment. This follows the existing immutable-release launch receipt's local-filesystem identity/time trust model: it requires immutable historical data and cooperating writers, does not defend against privileged restoration of file identities/change times, and is not an OS filesystem quota. A new operation always rehashes contents; receipt reuse does not cross operations. A policy that cannot accept that trust contract must retain `checkpointMode: "full"` and will stop if its finite aggregate I/O/time budget is exhausted. There is no silent downgrade from full hashing.

Receipts use `stream-dfs-sha256-v2`; old in-memory receipts/ledgers cannot be silently adopted. Prepare a **new independently reviewed** baseline through the read-only inspector, using a private request with all existing canonical roots and the explicit `scanBudget`:

```powershell
node scripts/local-release/scope-inventory.cjs --inspect <private-request.json>
```

The inspector returns only root identities, complete receipt, resource counters and effective limits on stdout; bounded segment progress without file contents goes to stderr. It does not create an adoption ledger, approve an exception, copy data, delete files, change permissions or control any process. Incomplete results are never usable baselines. The virtual-scale regression covers 1,049,601 entries with zero physical fixture files; it proves bounded algorithmic storage and complete traversal, **not production disk throughput or a successful production scan**. Real topology/fanout/reparse behavior and elapsed verification budget still require the production owner's read-only acceptance before adoption.

A self-contained package intentionally pins its own Node executable so startup and rollback do not depend on a mutable machine-wide runtime. Previously `build.cjs` used a new timestamp directory on every invocation and `copyFileSync(process.execPath, release/runtime/node.exe)` created another runtime. Successful packages were never retired: only a failed invocation's owned output was removed. Whole-package installation copied that runtime again into the installation root. The cumulative build quota was not a retrospective cleanup policy, and there was no completed-package count limit or verified-candidate reuse.

### Separate generation and installation boundaries

The build workspace now permits at most three direct package/output directories, a cumulative 768 MiB default across the entire build root, and a 4 GiB post-allocation volume reserve. Registered helper caches and `worktrees` do not consume a package slot but their regular bytes still consume that **build workspace** quota. Unknown/interrupted outputs occupy slots. A reservation for two outputs must use `begin(root, bytes, { packages: 2 })` and register both new direct directories. Exhaustion refuses generation; it never evicts existing output. Inventory limits and early over-count/byte rejection prevent an unbounded historical scan.

Before compiling, the builder can return an existing package only after exact source commit, source-input hash, layout, schema compatibility, Node version and runtime SHA comparison, complete byte/metadata verification and absence of an active build claim. Repeated attempts at the same frozen candidate return the same directory without another Node copy. Corrupt or mismatched packages are preserved and rejected.

An existing production `.local-releases` root can also contain source worktrees, nested build history, helper caches and historical installed packages. It is incorrect to apply the build root's three-output count or cumulative byte quota to that composite directory as though every entry were a live installed role. `install-lifecycle.cjs` therefore provides a distinct installation protocol. It admits the **current running package, one verified compatible rollback and one frozen candidate**, at most three distinct package IDs and **768 MiB total regular-file bytes across those roles**. It checks actual volume free space before and after allocation, including rounded new-file/directory/link overhead, with at least 4 GiB left. All files on the volume, including historical packages and worktrees, affect that physical reserve. This does not raise a threshold, turn the budget into a per-package quota, or relabel historical bytes as freed space.

The first adoption requires the exact reviewed list of existing historical installed IDs outside those roles (`adoptLegacy`, at most 128 IDs). Detection is shallow and bounded: a direct directory with `release.json` or `runtime/node.exe` is an installed artifact; nested worktree/build outputs are governed by their own generation root. `.release-lifecycle.json` freezes this legacy list and the managed role IDs. Legacy packages remain held, physically present and unavailable for implicit promotion. The baseline cannot grow on subsequent attempts. An unknown new installed artifact is rejected. Any previous managed role that drops out of the next three-role plan but remains on disk causes `RELEASE_RETIREMENT_APPROVAL_REQUIRED` before copying. It cannot be silently absorbed into legacy history. After a separately reviewed and approved exact retirement, the next bounded round can proceed. No retirement/delete command is included here.

Thus an old installation can temporarily hold its fixed historical backlog plus the three managed roles. It must not be reported as having only three physical runtimes. The backlog remains a separately inventoried storage debt pending explicit disposition; no automatic deletion or ever-growing exception is permitted. Missing source provenance or unreadable Git objects require preservation and review. Shared read-only, content-addressed runtimes are a possible later change and are not implemented here.

### Reviewed installation protocol

The release owner freezes a private JSON plan before execution. All three proofs must contain the expected 40-character `sourceCommit` and SHA-256 of the complete `release.json`, derived from the independently verified packages. The existing active pointer must be format 1 and match `current`. Candidate and rollback paths refer to existing frozen packages; nothing is rebuilt or downloaded.

```json
{
  "root": "<existing production .local-releases>",
  "plan": {
    "current": "<active-package-id>",
    "candidate": "<absolute frozen-candidate-path>",
    "rollback": "<absolute frozen-compatible-rollback-path>",
    "proofs": {
      "current": { "sourceCommit": "<40 hex>", "manifestSha256": "<64 hex>" },
      "candidate": { "sourceCommit": "<40 hex>", "manifestSha256": "<64 hex>" },
      "rollback": { "sourceCommit": "<40 hex>", "manifestSha256": "<64 hex>" }
    }
  },
  "adoptLegacy": [
    "<each exact historical installed id outside the three roles>"
  ]
}
```

After separate approval of the concrete plan, only the production owner runs:

```powershell
node scripts/local-release/install-lifecycle.cjs --plan <reviewed-private-json>
```

The module has no service, SQLite, backup, process-kill or network operation. It serializes cooperating writers using the same owned `.build-budget.lock`, fully verifies source and existing target manifests/files/links, refuses mismatched targets, and reuses exact already-installed outputs. It persists the exact managed intent before copying so a terminated copy cannot become a new legacy baseline. An incomplete existing copy fails verification and requires review. It checks frozen proofs, active pointer and owner again before completion. Ordinary failure removes only this invocation's new identity-verified directories; a changed owner, active pointer or any changed output identity preserves output for review. It never overwrites a target or deletes a historical package. The caller retains responsibility for the already approved protected upgrade backup, schema compatibility acceptance, controlled switch and rollback protocol.

Installing this host tooling does not change the frozen application candidate. Its tooling SHA and CI evidence must be reviewed separately; it does not authorize rebuilding, changing the approved application SHA, deploying, restarting or deleting real history. Existing handwritten installation scripts must call `installPair(root, plan, options)` (or this reviewed-plan CLI), replacing the incorrect `buildBudget.begin(compositeRoot, pairBytes)` and whole-package `cpSync` path; merely importing the helper while keeping the old installer is insufficient. Nonparticipating historical scripts remain outside the protocol and must not be used for future releases.
