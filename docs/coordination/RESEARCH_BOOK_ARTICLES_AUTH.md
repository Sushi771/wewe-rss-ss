# `/book/articles` 的 `skey/vid` 认证来源复核（A 线）

日期：2026-09-30。范围：公开源码、提交历史、维护者资料与一手反馈；本轮**未读取本机私有凭据、未登录、未请求腾讯文章接口、未写生产库**。五篇目标文章是接入 Provider 前的验收门槛，不是研究或一次只读首屏验证的门槛。

## 结论与可执行候选

1. **旧 WeBook 并未实现取得 `skey/vid`。**[引入提交 `85a679d`](https://github.com/wnma3mz/wechat_articles_spider/commit/85a679db335adb63f9ff7be054c01cac4148c51f) 在 2021-02-10 新增的 [独立 `WechatBook.py`](https://github.com/wnma3mz/wechat_articles_spider/blob/85a679db335adb63f9ff7be054c01cac4148c51f/wechatarticles/WechatBook.py#L8-L42) 将两值作为构造参数，向 `https://i.weread.qq.com/book/articles` 发送 `skey`、`vid` 请求头；类注释称 `vid` 固定、`skey` 会变。2021-02-11 移入 [现存 `WeBook`](https://github.com/wnma3mz/wechat_articles_spider/blob/f8b31196e88045d079901812ea064ad4953d62a6/wechatarticles/ArticlesUrls.py#L641-L673) 后仍无登录或续期函数。**它当时能够请求的直接原因是调用者在仓库外提供凭据**；凭据最初来自何处，仓库并未证明，不能推断成某个 Web Cookie。
2. **2026 年仍有另一条 `vid/skey` 一手代码证据，值得继续核查。**MIT 许可的 [weread-shelf-organizer 固定提交 `7ffef5c`](https://github.com/tanyaqiong31029/weread-shelf-organizer/tree/7ffef5c0111103c746b53ea607acb798ee5b8903) 从已登录的**腾讯微信读书 Mac 客户端**本地日志解析 `vid/skey`，再作为自定义头访问同一主机的 `/shelf/sync`；[提取和头代码](https://github.com/tanyaqiong31029/weread-shelf-organizer/blob/7ffef5c0111103c746b53ea607acb798ee5b8903/scripts/weread_shelf.py#L44-L96)、[验证与重启代码](https://github.com/tanyaqiong31029/weread-shelf-organizer/blob/7ffef5c0111103c746b53ea607acb798ee5b8903/scripts/weread_shelf.py#L145-L185)。作者 [README 自述](https://github.com/tanyaqiong31029/weread-shelf-organizer/blob/7ffef5c0111103c746b53ea607acb798ee5b8903/README.md#L24-L41) 真机迁移 2888 本；这不是本账号复现，也没有 `/book/articles` 成功回包。其 Windows/Linux 模式仅接收外部输入的凭据，不能在当前 Windows 环境独立取得或续期。Mac 脚本仅重启客户端再读日志，失效时仍可能需要本人重新登录；不能称服务器端自动续期。
3. **移动端 `accessToken` 与 `skey` 有一个明确的桥接关系，但不等于目标接口认证已解决。**近期 Go 实现 [WeRead-Kit `4b02a4b`](https://github.com/27Aaron/WeRead-Kit/tree/4b02a4b2d34355d425bf2b87ec3b924e98be29ee) 的 [正常登录解析](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/login.go#L220-L250) 得到 `vid/accessToken/refreshToken`，[移动业务请求头](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/client.go#L85-L91) 使用 `accessToken`；[Web 桥接](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/webapi.go#L110-L169) 将 **`accessToken` 放在 JSON 字段 `skey`**，向腾讯 `weread.qq.com/web/login/session/init` 换取服务器下发的 `wr_skey` Cookie。[续期](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/refresh.go#L60-L93) 用 `refreshToken` 向 `/login` 换新的 `accessToken`。这是 **Web 桥接入参名称**的明确映射，**不是** `i.weread.qq.com/book/articles` 旧 `skey` 请求头可用 `accessToken` 的证据；不可直接改名发探针。
4. **另找到旧浏览器扩展对同一端点的不同请求形状。**[Higurashi-kagome/wereader `a27b604` 的扩展后台](https://github.com/Higurashi-kagome/wereader/blob/a27b604dd7753734a27a47f341dbebbc6aef8917/src/worker/worker-popup.ts#L331-L348)和[分页监听](https://github.com/Higurashi-kagome/wereader/blob/a27b604dd7753734a27a47f341dbebbc6aef8917/src/worker/worker-listener.ts#L162-L178)直接 `fetch(i.weread.qq.com/book/articles?bookId=...&count=10&offset=...)`，没有显式 `skey/vid` 头或 `credentials: include`；[MV3 清单](https://github.com/Higurashi-kagome/wereader/blob/a27b604dd7753734a27a47f341dbebbc6aef8917/public/manifest.json#L66-L69)仅授予 i 主机网络访问权限。其参考的 [ellipse42 旧扩展 `38bbc46` 第 815–845 行](https://github.com/ellipse42/weread_helper_extension/blob/38bbc4685a8b6be1c28787ebcfbe2087e3cfd9f3/src/ui.js#L815-L845)也未显式加认证头。这是与 WeBook **有实质差异**的历史源码，不是 2026 匿名取文成功证据；以下专节限定它的运行条件。

因此 `/book/articles` 保持**待核实候选**。若后续能够从本人合法登录的腾讯客户端正常取得与 `i.weread.qq.com` 同一认证体系的 `vid/skey`（或找到该接口确实接受现有 token 的源码/一手响应证据），交独立 Probe 对目标做一次无重试、只读首屏，先看 HTTP/业务码和 `reviews` 字段；遇认证拒绝、验证码、限频立即停止。当前没有满足该条件的本机凭据来源证据，本轮未发请求。

### 旧浏览器扩展的无显式认证头首屏

`wereader@a27b604` [书架点击代码第 160–173 行](https://github.com/Higurashi-kagome/wereader/blob/a27b604dd7753734a27a47f341dbebbc6aef8917/src/popup/modules/popup-shelf.ts#L160-L173)仅当已在书架取得 `MP_WXS_` bookId 才打开公众号页；[后台首屏](https://github.com/Higurashi-kagome/wereader/blob/a27b604dd7753734a27a47f341dbebbc6aef8917/src/worker/worker-popup.ts#L331-L348)和[分页](https://github.com/Higurashi-kagome/wereader/blob/a27b604dd7753734a27a47f341dbebbc6aef8917/src/worker/worker-listener.ts#L162-L178)请求没有自定义鉴权头，期待 `reviews[].review.mpInfo`，[展示代码](https://github.com/Higurashi-kagome/wereader/blob/a27b604dd7753734a27a47f341dbebbc6aef8917/src/mpwx/mp.ts#L15-L57)读取 `doc_url/title/time/pic_url/content`。Chrome [扩展跨源请求说明](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)只证明 host permission 允许后台跨源访问；[Fetch 默认 credentials 为 `same-origin`](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch#including_credentials)，因此当前 MV3 后台从扩展源到 i 域名的这段**裸 `fetch` 不会自动携带该域 Cookie**。不能把 host permission 当作已登录认证、不能从代码存在推出服务端现在接受匿名请求。2020 年 `ellipse42` 是 `weread.qq.com` 内容脚本，运行环境与当前 MV3 后台又不同，不应混为同一会话条件。

[wereader README 第 49 行](https://github.com/Higurashi-kagome/wereader/blob/a27b604dd7753734a27a47f341dbebbc6aef8917/README.md#L49)称参考旧扩展的公众号浏览与书架管理功能目前已移除；旧调用仍留在源码。[维护者 2022 年 issue #56](https://github.com/Higurashi-kagome/wereader/issues/56)曾协助用户修复书架公众号显示，用户确认显示恢复；[issue #69](https://github.com/Higurashi-kagome/wereader/issues/69)中维护者称自己可显示，均**不是当前 `/book/articles` 成功 JSON 的回包证据**。2026-08 活跃 fork [`cheny-stack@5a6afa2`](https://github.com/cheny-stack/wereader/blob/5a6afa20cf1f9a863733ccfc9693f126de7c9c10/src/worker/worker-popup.ts#L331-L348)仍保留同一裸首屏调用，近期提交主题是文本选择，没有新认证链或近期成功反馈；2026-07 `geekspeng@bd25856` 的 `src` 则已无 `book/articles` 字面调用。Sourcegraph 以 `book/articles` 加 `repo:.*(weread|wechat).*` 并包括 fork 搜到的直接腾讯请求实现是旧 WeBook、上述两个扩展与端点目录；这是该索引范围，不是全 GitHub 不存在其他实现的证明。可交独立 Probe 审查一次**无凭据、无重试、只读首屏**是否仍给可判读 `reviews`；先只记 HTTP/业务码/结构，遇限制停止，不能因历史扩展源码直接接 Provider。此候选与 Web 搜索和旧 WeBook 自定义头均是不同假设。

### 第三轮：旧 `skey` 映射的独立复核（2026-09-30）

- 新增一份独立、固定版本的 Python 实现：[ylw1997/wereadapi `137c7aa` 第 203–210 行](https://github.com/ylw1997/wereadapi/blob/137c7aa214f947e192a490206b38bb524a63fdd4/tests/weread_api_test.py#L203-L210)把登录结果 `info.accessToken` 放入 JSON 字段 `skey`，请求 `POST /web/login/session/init`；[主机常量](https://github.com/ylw1997/wereadapi/blob/137c7aa214f947e192a490206b38bb524a63fdd4/tests/weread_api_test.py#L16)及[发送函数](https://github.com/ylw1997/wereadapi/blob/137c7aa214f947e192a490206b38bb524a63fdd4/tests/weread_api_test.py#L182-L184)限定主机为 `weread.qq.com`。[第 212–228 行](https://github.com/ylw1997/wereadapi/blob/137c7aa214f947e192a490206b38bb524a63fdd4/tests/weread_api_test.py#L212-L228)又从 `POST /web/login/renewal` 的 `Set-Cookie` 更新 `wr_vid/wr_skey/wr_rt`。这与前述 Go 桥接相互印证 **Web 会话初始化入参**，但这里是测试脚本，没有当前成功回包或 i 域名 `/book/articles` 请求。服务端下发的 `wr_skey`、请求体内名为 `skey` 的 `accessToken`、旧接口自定义 `skey` 头仍是三个需分别验证的位置，不能从字段重名推出同值或可续期。

### 本人现有移动凭据能否走 Web 桥接（2026-09-30，本地只读结构核查）

**具备一次隔离验证的凭据结构，但实时有效性尚未验证。**[旧客户端审计](../WEREAD_CLIENT_FLOW_AUDIT.md#L24-L33)记录本人正常二维码授权后从腾讯 `i.weread.qq.com/login` 取得 `vid/accessToken/refreshToken`，连同同设备 `deviceId` 保存于项目账号 JSON 的独立 `mobile` 对象；同一组移动凭据曾经续期成功。生产 [Web 登录实现](../../apps/server/src/weread/weread.service.ts#L90-L174)另从 `weread.qq.com/api/auth/getLoginInfo` 接收字段并把当时的 `accessToken` 赋给顶层 `wr_skey`，其[续期函数](../../apps/server/src/weread/weread.service.ts#L210-L255)只调用 `/web/login/renewal` 更新 Cookie。因此生产 Web 登录代码本身**不是**移动 `mobile` 对象的取得或续期代码。

对主工作区生产 SQLite 使用 `mode=ro` 与 `PRAGMA query_only=ON`，只执行账号数、JSON 路径存在性、非空和相等布尔查询，**没有向模型输出或保存凭据原值、长度、前后缀、哈希或账号 ID，也没有写库**。唯一账号的 token JSON 确有非空 `mobile.vid/mobile.accessToken/mobile.refreshToken/mobile.deviceId`，且无独立 `skey` 键；顶层另有 `wr_vid/wr_skey/wr_rt/accessToken/refreshToken`。`mobile.vid` 与顶层 `wr_vid` 相等，但 `mobile.accessToken` 与顶层 `accessToken` **不相等**，`mobile.refreshToken` 与顶层 `refreshToken` **不相等**；顶层 `accessToken` 与 `wr_skey` 相等。这些布尔事实说明本机保存了与旧 Web Cookie 赋值区分开的移动会话字段，结合上面的旧实验审计形成来源链，**不证明移动令牌今天仍被服务器接受**。`mobile` 对象没有保存时间或过期时间字段；顶层 Web `updateTime` 的记录约为 2026-09-26，只能给 Web 路径定时，不能给移动凭据判有效期。已知脱敏旧实验摘要和 `.env` 左侧键名没有另一个 `skey` 来源；私有 `WEREAD_API_KEY` 是 Gateway Key，不能用于此桥接。

**交独立 Probe 的一次低频方案。**依据 [WeRead-Kit 固定源码 `WebCookie` 第 110–177 行](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/webapi.go#L110-L177)及[独立 Python 实现](https://github.com/ylw1997/wereadapi/blob/137c7aa214f947e192a490206b38bb524a63fdd4/tests/weread_api_test.py#L203-L210)，从生产库**只读**提取同一个 `mobile` 对象，在隔离进程内仅向 `https://weread.qq.com/web/login/session/init` 发一次 `POST`，JSON 用 `vid=mobile.vid, skey=mobile.accessToken, rt=mobile.refreshToken, pf=0`；禁用自动重试/重定向，不混入顶层 Web Cookie，也不查询公众号。仅记录 HTTP 状态、脱敏业务码、`Set-Cookie` **名称**，并在进程内比较返回 `wr_vid` 是否与所用移动账号一致，不记录响应体或任何 Cookie 值。只有 HTTP 200、无失败业务码、服务器下发 `wr_skey` 且身份一致时，才允许在同一隔离会话中最多一次只读 `/web/shelf/sync` 验证 Web Cookie 能被服务器接受；这才证明 Web 桥接，不证明搜索列表或旧 `/book/articles`。若首个请求是 401、`-2012`、缺少 `wr_skey`、身份不一致、验证码或限频，立即停止本探针；移动令牌过期时可另行按[固定续期源码](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/refresh.go#L60-L100)和已成功旧实验设计**独立**一次刷新，但先处理 refreshToken 可能轮换及私人持久化，不能在本探针中自动重试或覆写生产账号。Web 桥接若成功，后续目标号搜索仍须单独实测号身份、发布时间、分页、正文与图片。

## 2026-09-30 Web 搜索 `-2012` 的认证边界

[总控已执行的一次隔离探针](MOBILE_WEB_SEARCH_PROBE.md#2026-09-30-总控一次在线执行)在合法移动账号 `POST /web/login/session/init` 后得到 HTTP 200，`wr_vid` 身份吻合，服务端下发五个 Cookie；同一 Node 进程只手工发送其中 `wr_vid/wr_skey/wr_rt` 三个到 `POST /web/wx_search_broker_proxy`，得到 HTTP 200 JSON `errCode=-2012`，无 `content`。本线未再读私有值或发目标查询。这次结果只排除**该 Node 请求上下文和三 Cookie 组合**；另两个服务器下发的 Cookie 是否必要尚无证据，不能把缺 Cookie、会话过期、跨源浏览器上下文或账号权限任一个写成确定原因。

同一端点的固定开源实现 [`dailyoozoo/weread-mp-fetch@2b4fd61`](https://github.com/dailyoozoo/weread-mp-fetch/tree/2b4fd61d921b029075ecad3963a8fbc9568d0fc0)要求处于 `https://weread.qq.com` 页面，[`src/weread.js` 第 337–369 行](https://github.com/dailyoozoo/weread-mp-fetch/blob/2b4fd61d921b029075ecad3963a8fbc9568d0fc0/src/weread.js#L337-L369)在页面内以 `fetch`、`credentials: 'include'` 发送搜索 POST；第 365 行也承认页面脚本设置的 `Referer` 由浏览器实际控制。[第 421–444 行](https://github.com/dailyoozoo/weread-mp-fetch/blob/2b4fd61d921b029075ecad3963a8fbc9568d0fc0/src/weread.js#L421-L444)把 `-2010/-2012` 归入认证失败类，但并未判明产生环节。[其接口记录第 79–86、185–192 行](https://github.com/dailyoozoo/weread-mp-fetch/blob/2b4fd61d921b029075ecad3963a8fbc9568d0fc0/docs/INTERFACE.md#L185-L192)报告旧 `session.json` 快照下同一搜索接口出现 `-2012`、持续浏览器分区可正常工作；这是作者的一手条件对照，不能反推本次**刚签发**会话已经过期。[`src/session.js` 第 118–160、197–245、294–321 行](https://github.com/dailyoozoo/weread-mp-fetch/blob/2b4fd61d921b029075ecad3963a8fbc9568d0fc0/src/session.js#L197-L245)读取并合并完整的浏览器 Cookie jar，处理轮换，而非仅固定三个 Cookie。另一个固定实现 [`DepengWang/we-mp-rss@15d0d33` 第 147–205 行](https://github.com/DepengWang/we-mp-rss/blob/15d0d33fd6d1a14a20c6e860d98d3a30738bdb0f/core/weread_cookie_refresh.py#L147-L205)用只读 `/web/shelf/sync` 区分有效会话、`-2010/-2012` 和未知响应；这提供搜索前的独立健康检查，却不证明该检查通过就有搜索权限。其他端点把 `-2012` 解释为过期或重复 Cookie，也不能代替本搜索代理的官方错误定义。

公开腾讯 PC 搜索 bundle [上述 `read_search.fc739bbf.js`](https://search.wxqcloud.qq.com/t/searchweb/search/weixin-search-outlinks/26090701/js/read_search.fc739bbf.js) 字符偏移约 65,386–65,600 的请求只有 `query/offset/searchid/searchcookies` 和 `withCredentials: true`；没有附加自定义 Cookie、CSRF、`Origin` 或 `Referer` 头。全文件无 `-2012` 专门分支。其依赖 [`chunk-vendors.2d60503b.js`](https://search.wxqcloud.qq.com/t/searchweb/search/weixin-search-outlinks/26090701/js/chunk-vendors.2d60503b.js) 本轮 1,562,473 字节，SHA-256 `AF2D79D646903B072FB6F73004D952CE8951E8BB3F88E9817692636422145E7E`：字符偏移约 127,952 是 axios 默认 `xsrfCookieName: 'XSRF-TOKEN'`、`xsrfHeaderName: 'X-XSRF-TOKEN'`，约 395,900 是跨源请求在 `withCredentials` 时读取当前页面 Cookie 的 XSRF 适配器，约 1,211,967 是 `document.cookie` 读取实现。它仅证明**如果当前 `search.weixin.qq.com` 页面确有该 Cookie，axios 可能加头**；未证明 Cookie 存在、腾讯服务端要求该头、或 Node 失败出于 CSRF。不得伪造或猜参数。当前公开 `weread.qq.com/` 首页引用的四个静态包（`D5nOnlJZ-legacy.js`、`BZ6SsvaW-legacy.js`、`9oq92R5p.js`、`BVQc4ULa.js`）的定点扫描未发现字面 `-2012`、`wx_search_broker_proxy` 或 `session/init`；动态分包与服务端逻辑不在此检索结论内。

**完整 Cookie jar 对照已执行，搜索没有发送。**[总控一次执行的脱敏记录](BROWSER_CONTEXT_COOKIE_JAR_PROBE.md#2026-09-30-总控复审后的一次在线结果)显示：非持久 Playwright `BrowserContext` 用同一合法 `mobile` 对象做一次 init，HTTP 200，服务端下发 `wr_pf/wr_ql/wr_rt/wr_skey/wr_vid` 五个 Cookie，均适用于书架和搜索路径，`wr_vid` 与输入 `mobile.vid` 相同；在该 Context 的共享 jar 中请求一次 `/web/shelf/sync`，HTTP 200 JSON `errCode=-2012`。健康门禁随即停止，搜索 0、页面导航 0、验证码/重试/分页 0。Playwright [官方文档](https://playwright.dev/docs/api/class-apirequestcontext)说明 `context.request` 使用共享 jar，但本次没有观察线上请求头，也没有测试页面实际登录流程。此结果使“Node 只带三 Cookie 是**书架会话失败的唯一原因**”不成立；仍未直接测试完整 jar 对搜索端点的结果，不能推断搜索账号无权。

**init 200 并不证明服务端已认证。**[`27Aaron/WeRead-Kit` 2026-09 issue #48](https://github.com/27Aaron/WeRead-Kit/issues/48)的项目参与者给出一手对照：向 `/web/login/session/init` 放入无效 `skey/rt` 仍得到 HTTP 200、`success:1` 和相应 `Set-Cookie`，后续 Web 阅读请求却因会话失效失败；一次合法移动 `Refresh` 后再桥接，作者报告请求恢复。固定源码 [`webapi.go` 第 111–170 行](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/webapi.go#L111-L170)把 `mobile.accessToken` 填入 init JSON `skey`，但仅把 init 的 HTTP 401、显式 `-2012`、缺 `wr_skey` 当失败；[`farm_recovery_test.go` 第 12–18 行](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/farm_recovery_test.go#L12-L18)及[第 54–68 行](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/farm_recovery_test.go#L54-L68)用 mock 固化“死 Cookie”场景。issue 的无效字段实验是**作者的一手观察**，mock 是回归测试，两者均非腾讯规范；新探针与该现象相容，但不能由此确定本人 `mobile.accessToken` 已过期、`refreshToken` 仍有效，或页面上下文完全无关。另一份固定实现 [`DepengWang` 第 147–205 行](https://github.com/DepengWang/we-mp-rss/blob/15d0d33fd6d1a14a20c6e860d98d3a30738bdb0f/core/weread_cookie_refresh.py#L147-L205)也把书架 `-2012` 列入无效 Web 会话分类；这是开源作者判断，不是官方错误定义。

**一次移动 Refresh 的复审门禁（本线未执行）。**本人 `mobile` 字段来自正常微信扫码后 `POST i.weread.qq.com/login`，旧实验已用同设备字段续期成功，随后 `/mp/chapters` 仍 `-2041`；[脱敏审计第 24–35 行](../WEREAD_CLIENT_FLOW_AUDIT.md#L24-L35)证明此次可研究的差异是**刷新后的 Web 会话健康**，不是再测已失败的移动 `/mp/chapters`。先可考虑只读一次移动 [`GET /shelf/sync`](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/shelf.go#L24-L49)，其固定头是 `vid/accessToken`：若该移动会话有效，优先追 Web init/书架的独立差异；若明确 401/`-2012`，才进入**至多一次**移动刷新审查。刷新请求只按同设备 [weread-omni `token.ts` 第 50–86 行](https://github.com/teng-lin/weread-omni/blob/88bd2e095d7d7ee423eaadf8f40653e72c5be6d4/src/auth/token.ts#L50-L86)或独立 [WeRead-Kit `refresh.go` 第 60–100 行](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/refresh.go#L60-L100)的 `POST i.weread.qq.com/login` 固定形状；不猜 UA、签名、头、参数，不因响应异常自动重试或扫码。只在同一 `vid`、HTTP 成功且返回非空新 `accessToken` 时接受；`refreshToken` 未返回则沿用旧值，返回则视为可能轮换，[`TokenManager` 第 232–254 行](https://github.com/teng-lin/weread-omni/blob/88bd2e095d7d7ee423eaadf8f40653e72c5be6d4/src/auth/token.ts#L232-L254)要求变化后立即持久化。

刷新**可能使原 `refreshToken` 不可再用**：不能做“只放内存试完就丢”的在线实验。执行前须核验生产 SQLite 一致性备份、在隔离私有副本演练同账号 token 结构与写入、确认无另一个进程同时消费该移动凭据，并准备仅私有且不入 Git 的新 token 恢复位置。在线刷新成功后先在内存核对 `vid` 和响应结构，立即把**完整的新 `mobile` 对象**写入经演练的私有恢复副本并核验可读，再由总控按生产写库门禁决定是否切换；即使随后 Web init 或 shelf 失败，也必须保留轮换后的凭据。只输出 HTTP/业务码、同账号布尔和字段存在/轮换布尔，不输出值、长度或哈希。刷新失败、账号不符、验证码或限频均停止后续 Web 请求并保留旧备份；如果新 token 的私有写入失败，进程应保留内存中的新凭据并停止其他请求，先修复私有持久化，不能退出而丢失可能已轮换的唯一有效凭据。没有安全持久化条件就停在静态证据审查。后续新凭据的 Web init + 书架健康应另定一次有上限探针，不能借刷新之名自动连发搜索或旧 `/book/articles`。

## 下一轮有判别力的工作

1. 核对 **Mac 官方客户端 `vid/skey`** 与已合法取得的移动/Eink `vid/accessToken` 是否为同一认证产物：只能比较本人正常登录获得的**字段来源和是否同值**，不输出值、长度、前后缀或哈希；没有 Mac 条件时继续追公开客户端或开源正常登录代码，不要求用户先安装或扫码。
2. 检查公开的腾讯客户端/维护中项目是否明确记录 `i.weread.qq.com/book/articles` 接受 `accessToken` 头或 `skey` 头，及其账号授权范围。Web 桥接的 JSON `skey` 命名不满足这个条件。
3. 若已合法获得同一客户端体系的 `vid/skey`，再由独立 Probe 按旧 WeBook 的 `GET /book/articles?bookId=MP_WXS_3895431412&count=20&offset=0&synckey=<秒>` 作一次只读首屏；先记录状态、错误类别、`reviews` 是否存在和字段名，不保存正文、原始响应或凭据。取得真实条目后再单独核验至少五篇不同文章的目标号身份、稳定 ID、真实发布时间及分页、正文、图片；旧库 194 篇不能充作新来源样本。

本线排除的只是**用 WeBook 源码直接自动登录**、**Web Cookie 自动跨域认证**、**把 Gateway Key 或移动 token 仅按名字重命名当作旧 skey**。尚未排除同一腾讯主机使用合法 Mac/iOS `skey` 请求 `/book/articles` 的可能，也未排除其他自建取文路线。
