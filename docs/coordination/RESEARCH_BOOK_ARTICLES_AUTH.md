# `/book/articles` 的 `skey/vid` 认证来源复核（A 线）

日期：2026-09-30。范围：公开源码、提交历史、维护者资料与一手反馈；本轮**未读取本机私有凭据、未登录、未请求腾讯文章接口、未写生产库**。五篇目标文章是接入 Provider 前的验收门槛，不是研究或一次只读首屏验证的门槛。

## 结论与可执行候选

1. **旧 WeBook 并未实现取得 `skey/vid`。**[引入提交 `85a679d`](https://github.com/wnma3mz/wechat_articles_spider/commit/85a679db335adb63f9ff7be054c01cac4148c51f) 在 2021-02-10 新增的 [独立 `WechatBook.py`](https://github.com/wnma3mz/wechat_articles_spider/blob/85a679db335adb63f9ff7be054c01cac4148c51f/wechatarticles/WechatBook.py#L8-L42) 将两值作为构造参数，向 `https://i.weread.qq.com/book/articles` 发送 `skey`、`vid` 请求头；类注释称 `vid` 固定、`skey` 会变。2021-02-11 移入 [现存 `WeBook`](https://github.com/wnma3mz/wechat_articles_spider/blob/f8b31196e88045d079901812ea064ad4953d62a6/wechatarticles/ArticlesUrls.py#L641-L673) 后仍无登录或续期函数。**它当时能够请求的直接原因是调用者在仓库外提供凭据**；凭据最初来自何处，仓库并未证明，不能推断成某个 Web Cookie。
2. **2026 年仍有另一条 `vid/skey` 一手代码证据，值得继续核查。**MIT 许可的 [weread-shelf-organizer 固定提交 `7ffef5c`](https://github.com/tanyaqiong31029/weread-shelf-organizer/tree/7ffef5c0111103c746b53ea607acb798ee5b8903) 从已登录的**腾讯微信读书 Mac 客户端**本地日志解析 `vid/skey`，再作为自定义头访问同一主机的 `/shelf/sync`；[提取和头代码](https://github.com/tanyaqiong31029/weread-shelf-organizer/blob/7ffef5c0111103c746b53ea607acb798ee5b8903/scripts/weread_shelf.py#L44-L96)、[验证与重启代码](https://github.com/tanyaqiong31029/weread-shelf-organizer/blob/7ffef5c0111103c746b53ea607acb798ee5b8903/scripts/weread_shelf.py#L145-L185)。作者 [README 自述](https://github.com/tanyaqiong31029/weread-shelf-organizer/blob/7ffef5c0111103c746b53ea607acb798ee5b8903/README.md#L24-L41) 真机迁移 2888 本；这不是本账号复现，也没有 `/book/articles` 成功回包。其 Windows/Linux 模式仅接收外部输入的凭据，不能在当前 Windows 环境独立取得或续期。Mac 脚本仅重启客户端再读日志，失效时仍可能需要本人重新登录；不能称服务器端自动续期。
3. **移动端 `accessToken` 与 `skey` 有一个明确的桥接关系，但不等于目标接口认证已解决。**近期 Go 实现 [WeRead-Kit `4b02a4b`](https://github.com/27Aaron/WeRead-Kit/tree/4b02a4b2d34355d425bf2b87ec3b924e98be29ee) 的 [正常登录解析](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/login.go#L220-L250) 得到 `vid/accessToken/refreshToken`，[移动业务请求头](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/client.go#L85-L91) 使用 `accessToken`；[Web 桥接](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/webapi.go#L110-L169) 将 **`accessToken` 放在 JSON 字段 `skey`**，向腾讯 `weread.qq.com/web/login/session/init` 换取服务器下发的 `wr_skey` Cookie。[续期](https://github.com/27Aaron/WeRead-Kit/blob/4b02a4b2d34355d425bf2b87ec3b924e98be29ee/internal/weread/refresh.go#L60-L93) 用 `refreshToken` 向 `/login` 换新的 `accessToken`。这是 **Web 桥接入参名称**的明确映射，**不是** `i.weread.qq.com/book/articles` 旧 `skey` 请求头可用 `accessToken` 的证据；不可直接改名发探针。

因此 `/book/articles` 保持**待核实候选**。若后续能够从本人合法登录的腾讯客户端正常取得与 `i.weread.qq.com` 同一认证体系的 `vid/skey`（或找到该接口确实接受现有 token 的源码/一手响应证据），交独立 Probe 对目标做一次无重试、只读首屏，先看 HTTP/业务码和 `reviews` 字段；遇认证拒绝、验证码、限频立即停止。当前没有满足该条件的本机凭据来源证据，本轮未发请求。

## 历史、fork 与其他语言核查

- WeBook 的路径、头和 `reviews[].review` 提取始于上述 2021 提交；[2022-01-14 最后一次改该文件的提交](https://github.com/wnma3mz/wechat_articles_spider/commit/77704ff)没有增加认证链。`git grep` 固定上游 HEAD `f8b3119` 的可执行 Python 源码，`skey` 只在 WeBook 的注释、构造参数、头部出现；未找到生成/读取它的函数。上游 Apache-2.0。
- GitHub forks API 当次列出约 757 个 fork；按近期 `pushed_at` 缩小后核查 `Fargger`、`hongyu9000`、`liusishan`（HEAD 与上游相同）、`qiye9019`（2025 仅多一行 README“安装”）、`yudataguy`、`Longliveping`、`hbrzbj`（相关 WeBook 文件与上游无差异）及 `Marshall-Hu`（2026 近期 CI 改动、所含 WeBook 仍只要求外传 `skey/vid`）。**这只覆盖选定的近期 fork，不能宣称 757 个 fork 全部无新代码。**[上游 issue #58](https://github.com/wnma3mz/wechat_articles_spider/issues/58)问的是微信文章页面 `key`，不是 WeBook `skey`；未找到上游 issue 给出可复用的 WeBook 登录链。
- TypeScript [weread-omni](https://github.com/teng-lin/weread-omni/blob/88bd2e095d7d7ee423eaadf8f40653e72c5be6d4/src/profile.ts#L20-L27)走 `accessToken`；另一个 [weread-client](https://github.com/djyde/weread-client/blob/d38319eb4fd31532c7f450e66884b2181cc1ac6e/src/client.ts#L143-L159)向 `weread.qq.com` Web API 请求，浏览器带 Cookie 或由调用者传 headers，未生成 i 域名 `skey`。Go 的 WeRead-Kit 是上文明确的移动到 Web 桥接。Rust [rm-weread Web 登录](https://github.com/JIACHENG135/rm-weread/blob/747136448421dfed474a8360e790215a79607497/src/login.rs#L78-L95)独立复现 `webLoginVid/accessToken/refreshToken → wr_vid/wr_skey/wr_rt`，但其 `X-Skey` 只送 Web 用户/API Key 接口；另一个 Rust [nlimpid/weread](https://github.com/nlimpid/weread/blob/120c7bb8b9fe0ace602a79c58edd6eec07df35c0/weread/src/client.rs#L67-L98)只向官方 Gateway 发送 Bearer Key。针对 Go/Rust `book/articles + skey/vid` 的公开索引查询未找到独立实现；这不是不存在的证明。
- 2026-09-22 的 [weread-mp-fetch 固定提交](https://github.com/dailyoozoo/weread-mp-fetch/tree/2b4fd61d921b029075ecad3963a8fbc9568d0fc0)提供另一份 Web 会话生命周期证据：[session.js 第 40–42 行](https://github.com/dailyoozoo/weread-mp-fetch/blob/2b4fd61d921b029075ecad3963a8fbc9568d0fc0/src/session.js#L40-L42)限定 `weread.qq.com` Cookie 与 `wr_vid/wr_skey`，[第 173–245 行](https://github.com/dailyoozoo/weread-mp-fetch/blob/2b4fd61d921b029075ecad3963a8fbc9568d0fc0/src/session.js#L173-L245)从浏览器读取并注入 Cookie，[第 294–321 行](https://github.com/dailyoozoo/weread-mp-fetch/blob/2b4fd61d921b029075ecad3963a8fbc9568d0fc0/src/session.js#L294-L321)保存轮换后的值；[接口说明](https://github.com/dailyoozoo/weread-mp-fetch/blob/2b4fd61d921b029075ecad3963a8fbc9568d0fc0/docs/INTERFACE.md#L7-L17)访问的是 `POST weread.qq.com/web/wx_search_broker_proxy`。它没有构造旧接口的 `skey/vid` 自定义头或请求 `/book/articles`，故只证明 Web 搜索认证的生命周期，**不能将同名 Cookie 转换为旧 ArticleService 认证**。
- [2025 Android 逆向文章](https://yumi1.top/weread-security-analysis-2/)给出 `refreshToken` 登录返回 `skey` 的示例，但响应字段是 `data.skey`、示例日期为 2022 年占位时间戳；[同作者另一页](https://yumi1.top/weread-security-analysis-4/)却从 JSON 顶层解构 `vid/skey` 且用 `your_refresh_token`。不能将两段样例当作 2025/2026 的实际成功响应或可直接运行的续期代码。[2026 iOS 使用者记录](https://whchen.dev/notes/weread-reading-page-01)说明旧 `skey` 曾从抓包取得、过期后人工更新；本任务禁止以抓包作为产品运行方式，因此仅作生命周期旁证。
- [2025 GitHubPoster 用户报告](https://github.com/yihong0618/GitHubPoster/issues/112)里 Web Cookie 同时有 `wr_skey` 与名为 `skey` 的字段，向 `i.weread.qq.com/readdetail` 仍返回 `-2012`；它测试的是 Cookie，不是 `/book/articles` 的自定义头。与 OpenCLI 反馈共同支持“不把 Cookie 字段名等同移动请求头”的谨慎边界。

### 第三轮：旧 `skey` 映射的独立复核（2026-09-30）

- 新增一份独立、固定版本的 Python 实现：[ylw1997/wereadapi `137c7aa` 第 203–210 行](https://github.com/ylw1997/wereadapi/blob/137c7aa214f947e192a490206b38bb524a63fdd4/tests/weread_api_test.py#L203-L210)把登录结果 `info.accessToken` 放入 JSON 字段 `skey`，请求 `POST /web/login/session/init`；[主机常量](https://github.com/ylw1997/wereadapi/blob/137c7aa214f947e192a490206b38bb524a63fdd4/tests/weread_api_test.py#L16)及[发送函数](https://github.com/ylw1997/wereadapi/blob/137c7aa214f947e192a490206b38bb524a63fdd4/tests/weread_api_test.py#L182-L184)限定主机为 `weread.qq.com`。[第 212–228 行](https://github.com/ylw1997/wereadapi/blob/137c7aa214f947e192a490206b38bb524a63fdd4/tests/weread_api_test.py#L212-L228)又从 `POST /web/login/renewal` 的 `Set-Cookie` 更新 `wr_vid/wr_skey/wr_rt`。这与前述 Go 桥接相互印证 **Web 会话初始化入参**，但这里是测试脚本，没有当前成功回包或 i 域名 `/book/articles` 请求。服务端下发的 `wr_skey`、请求体内名为 `skey` 的 `accessToken`、旧接口自定义 `skey` 头仍是三个需分别验证的位置，不能从字段重名推出同值或可续期。
- 本轮将 `"i.weread.qq.com" + "skey" + "refreshToken/accessToken"`、`"book/articles" + "skey/vid"` 及 2025–2026 年公开仓库/网页作为检索边界，并核对了 [CyrusNee/weread `cab52f3` 正常登录解析](https://github.com/CyrusNee/weread/blob/cab52f3035008f2df8ce6cce6e821cfb819e2bca/src/auth/qrlogin.ts#L240-L276)、[续期](https://github.com/CyrusNee/weread/blob/cab52f3035008f2df8ce6cce6e821cfb819e2bca/src/auth/token.ts#L95-L134)、[客户端认证头](https://github.com/CyrusNee/weread/blob/cab52f3035008f2df8ce6cce6e821cfb819e2bca/src/profile.ts#L20-L27)：这份近期 fork 仍解析/发送 `accessToken`，没有在这些认证代码中生成旧 `skey` 头。[Yumi 的 2025 Android 反编译说明](https://yumi1.top/weread-security-analysis-1/)展示 `Account` 的 `accessToken/refreshToken` 字段及日志读取，但未公开一条可复核的 `Account → skey` 请求头数据流；其另页 `skey` 示例仍保留上文所述字段层级冲突。搜索结果中的 `wrk-` Gateway、Web `wr_skey` 续期和移动 `accessToken` 均未补齐 `/book/articles` 的认证链。这是**本轮所查证据不足**，不等于旧接口永久不可用，也不排除尚未索引的客户端实现或近期 fork。

## 新专项：正常 Web 登录到「搜一搜」的会话链

这是一条与旧 ArticleService 不同的候选路线。2026 年开源 [legal-weekly-briefing 固定提交 `2f74acf`](https://github.com/5tnb6xgsm5-ops/legal-weekly-briefing/tree/2f74acfd8eda51441278d668c9d3c00e5c3c21ad) 的 [登录脚本](https://github.com/5tnb6xgsm5-ops/legal-weekly-briefing/blob/2f74acfd8eda51441278d668c9d3c00e5c3c21ad/scripts/weread_login.py#L32-L99)用有头浏览器打开腾讯 `weread.qq.com`，等待本人扫码，检测 `wr_vid` 后稍等 `wr_skey` 落定，再以 Playwright `storage_state` 写入私人文件。它的[定时抓取脚本](https://github.com/5tnb6xgsm5-ops/legal-weekly-briefing/blob/2f74acfd8eda51441278d668c9d3c00e5c3c21ad/scripts/fetch_weread_week.py#L66-L85)从文件**只取 Cookie 数组**，在新无头 BrowserContext 里 `add_cookies`，先打开 `weread.qq.com`，[再导航](https://github.com/5tnb6xgsm5-ops/legal-weekly-briefing/blob/2f74acfd8eda51441278d668c9d3c00e5c3c21ad/scripts/fetch_weread_week.py#L178-L212)至 `search.weixin.qq.com/cgi-bin/newsearchweb/userclientjump?path=page/search/weread`。作者在 [STATUS](https://github.com/5tnb6xgsm5-ops/legal-weekly-briefing/blob/2f74acfd8eda51441278d668c9d3c00e5c3c21ad/STATUS.md#L21-L49)自述 2026-07-31 四个号、35 条原文直链和三次运行差异；这是作者的一手反馈，尚非本账号验收。[2025 用户分享的搜索模板](https://getquicker.net/Common/Topics/ViewTopic/32800)也注明先在浏览器登录微信读书，但没有揭示会话桥接机制。

**腾讯静态 JS 一手证据。**不带查询词访问公开 `userclientjump?path=page/search/weread&platform=pc` HTML 后，其引用的 [`read_search.fc739bbf.js`](https://search.wxqcloud.qq.com/t/searchweb/search/weixin-search-outlinks/26090701/js/read_search.fc739bbf.js) 为 68,998 字节、SHA-256 `E5E090EE6B6180DE2ED72EE3EEEBDCDAB9A10C5C0F5C95F442FD7940730F7089`。该单行文件字符偏移约 65,355–65,600 的 PC 分支调用 `axios.request`，`POST https://weread.qq.com/web/wx_search_broker_proxy`，JSON 字段是 `query/offset/searchid/searchcookies`，并显式 `withCredentials: true`。响应 `errCode === -2010` 时跳过 `handleApiRes`，其他回包把 `content.offset/searchID/cookies/continueFlag` 写回页面状态，`onScrollEnd` 在 `continueFlag` 为真时使用该 offset 续取（约 65,981–66,880）；`searchcookies` 是**响应内容中的分页状态**，不是浏览器 `wr_skey` Cookie。静态文件没有解释 `-2010` 的业务含义，也未给 `-2012` 专门分支；HTTP/CORS 错误只进入 console 日志。上述是公开客户端行为，不是本账号成功回包或服务端保证；本轮未带凭据、未发送目标查询。

下一步可由独立 Probe 在本人已有合法登录环境里做**一次隔离、低频、只读页面验证**：现有[单滚动探针](WEREAD_NATURAL_SCROLL_PROBE.md)只统计官方页面首屏与一次自然滚动的脱敏卡片数、目标号名匹配数和验证提示；[直接 Web POST 探针](WEB_SEARCH_BROKER_PROBE.md)另可记录一次首屏的脱敏业务状态。两者均不读取 Cookie、保存原始页面或正文，遇验证码或明确限制即停止。会话健康需与搜索页实际结果分别判定，不能以 `wr_vid` 存在、单次 `/web/shelf/sync` 成功或滚动后条数代替搜索验收。该路线不使用旧 `/book/articles` 的 `skey/vid` 请求头；三者不可按字段名互换。

**静态字段与分页边界。**同一 bundle 约偏移 3,390、3,900–5,550 的文章组件把结果项 `title/desc/thumbUrl/source.title/source.dateTime` 显示到页面，把 `docID + "&" + block.type` 放入 DOM `data-id`；约偏移 47,600–48,900 的 PC 点击逻辑对公众号项用 `window.open(item.doc_url, "_blank")`，一般 H5 项可用 `jumpInfo.jumpUrl || doc_url`。这些是候选文章标题、展示来源、展示时间和链接字段；**没有直接证明 `source.dateTime` 是原始可信发布时间、`docID` 可跨次稳定，或 `source.title` 对应目标号的 `biz`**。约偏移 65,981–66,880 的 `handleApiRes` 在 `content` 为 null、`data` 缺失或空时置 `continueFlag=false`；有数据时用响应的 `offset/searchID/cookies/continueFlag` 更新状态，`onScrollEnd` 仅在 `continueFlag` 为真时调用 `_get`，后者用 `isLoading` 防止并发。PC 请求体只有 `query/offset/searchid/searchcookies`，该 bundle 没有 `biz/__biz/fakeid` 或作者稳定 ID 字段可按号过滤，因此搜索覆盖率与结果混入程度仍未知，须以目标文章原文链接核号。它没有完整的“认证失败”状态机：`errCode=-2010` 被跳过、其他 HTTP/CORS 错误只写 console，均不能直接解释为账号无权或列表结束。

## 下一轮有判别力的工作

1. 核对 **Mac 官方客户端 `vid/skey`** 与已合法取得的移动/Eink `vid/accessToken` 是否为同一认证产物：只能比较本人正常登录获得的**字段来源和是否同值**，不输出值、长度、前后缀或哈希；没有 Mac 条件时继续追公开客户端或开源正常登录代码，不要求用户先安装或扫码。
2. 检查公开的腾讯客户端/维护中项目是否明确记录 `i.weread.qq.com/book/articles` 接受 `accessToken` 头或 `skey` 头，及其账号授权范围。Web 桥接的 JSON `skey` 命名不满足这个条件。
3. 若已合法获得同一客户端体系的 `vid/skey`，再由独立 Probe 按旧 WeBook 的 `GET /book/articles?bookId=MP_WXS_3895431412&count=20&offset=0&synckey=<秒>` 作一次只读首屏；先记录状态、错误类别、`reviews` 是否存在和字段名，不保存正文、原始响应或凭据。取得真实条目后再单独核验至少五篇不同文章的目标号身份、稳定 ID、真实发布时间及分页、正文、图片；旧库 194 篇不能充作新来源样本。

本线排除的只是**用 WeBook 源码直接自动登录**、**Web Cookie 自动跨域认证**、**把 Gateway Key 或移动 token 仅按名字重命名当作旧 skey**。尚未排除同一腾讯主机使用合法 Mac/iOS `skey` 请求 `/book/articles` 的可能，也未排除其他自建取文路线。
