# 官方搜索时间与既有原文时间：离线对照

2026-09-30。本轮只读当前私有搜索候选、既存原文核验清单和生产 SQLite；网络请求与生产写入均为 0。本文仅保留计数和秒差，不记录文章身份、标题、链接或原始页面。

## 时间证据的来源

历史 [`verifyDesktopEvidence`](../../apps/server/scripts/verify-desktop-evidence.ts) 输出的私有 `verified-latest20.json` 含原文核验后的 `publishTime`。生成时的核验实现见 Git 提交 `1b9faae` 中 `apps/server/src/collection/desktop-wechat.ts` 的 `verifyCards`：逐条读取官方原文页，用 `articleIdentity` 校验公众号与 canonical 短链，用 `articlePublishTime(html)` 取得时间，任一身份、标题、时间失败则整批报错。该提交的 `article-page.ts` 中，`articlePublishTime` 从原文 HTML 的十位 `create_time`、`ct` 或 `CreateTime` 读取时间。既有[桌面修复审计](../DESKTOP_COLLECTION_REPAIR.md)及本机私有审计均把该文件记录为 20 篇原文核验结果。这里**只复用既有核验结果作为时间证据**；这条历史桌面采集方式不属于当前产品运行路线。

六条本次可比记录的原文 HTML 已不在本机，因此不能重新逐页复核字面 `ct`。保留的核验清单与历史可审代码构成其原文时间来源；本轮没有把搜索列表 `timestamp`、数据库 `publish_time`、`syncTime`、合集 `create_time` 或推算时间当作原文时间。旧库正文缓存均不含原文时间字段，单靠库内时间不能做这项对照。

## 匹配规则与结果

先要求搜索候选和旧库 `verified_source_url` 的 `__biz`、`mid`、`idx`、`sn` 四字段各出现一次且完全相等。再要求**同一旧库记录**的文章 ID 和 `source_url` 短链分别与原文核验清单的 ID、短链完全相等，且两边时间均为整数秒。只在这条证据链完整时计算 `搜索 timestamp − 原文 publishTime`。

| 检查点                                         | 数量 |
| ---------------------------------------------- | ---: |
| 已存官方搜索目标号候选                         |   11 |
| 与旧库四字段长链完全相等                       |    7 |
| 还能严格对应既有原文核验 ID 与短链             |    6 |
| 可计算可信原文秒差                             |    6 |
| 四字段虽相等、但缺少严格原文核验短链与 ID 对应 |    1 |

六条秒差升序为 **−53、−49、−44、−42、−1、0 秒**；负值 5 条、相等 1 条、正值 0 条，范围 **−53 至 0 秒**。这仅说明这六条旧文章的搜索时间比核验原文时间早 0–53 秒，不证明搜索时间对其他文章等于原文 `ct`，也不能用它替代原文时间验收。

余下四条搜索候选没有旧库四字段长链匹配，另有一条虽匹配旧库长链，但无法再用该行的 ID 与短链严格接到原文核验清单；均不计算秒差。现存另一份真实原文 HTML 与本批候选没有四字段交集，早先八份旧原文 HTML 当前未找到。尚未核实的搜索候选、此前触发验证或原文身份不符的候选，都不能凭此次时间对照计为新文章或恢复订阅。

本轮只读 SQLite 使用 `readOnly` 连接及 `PRAGMA query_only=ON`；搜索候选经既有私有记录校验函数读取。没有新增脚本、没有重发任何目标 URL。
