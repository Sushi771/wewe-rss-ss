# Provider 接入准备与副本验收（2026-09-29）

## 结论

现有后端具备受控接入的保存与导出链路；**尚无真实可用的新取文来源，不能启用生产订阅**。本轮仅加固 Provider 写入边界和 SQLite 副本保护工具，不新增来源、路由、管理页面或生产写库。目标号五篇真实不同文章及分页、正文、图片、持续更新仍须由来源实验验证。

## 已核对的工程边界

| 环节      | 当前实现与本轮处理                                                                                                                                                                                           | 接新来源时的要求                                                                                                                             |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider  | `SubscriptionProvider` 当前由 Wechat2RSS 实现，`ProviderPage` 标记近期窗口或存储历史窗口；新加 `assertProviderPage`，在图片请求和文章写入前检查同号、由完整原文链接推出的规范 ID、页内去重、时间形状与计数。 | 根据真实回包建立独立适配器及显式启用门，不能复用 Wechat2RSS 的 `id`、认证或字段猜测。当前接口只表示一页，没有已验证的分页/增量游标语义。     |
| 保存      | `TrpcService` 在运行/失败状态等任何写入前调用 SQLite 一致性备份；采集事务用 ID/原文链接匹配，疑似旧短链冲突时整批拒绝；重复更新只补旧记录的空来源、正文和图片，不以空值覆盖，也不改旧标题、发布时间或指标。  | 真正分页时先验证完整窗口及服务端游标；仅在页成功、身份与时间核验后推进持久检查点。失败页不得推进。单号生产写入前重新备份并在副本跑重复导入。 |
| 刷新/状态 | 手动刷新尝试时间持久化并有 15 分钟冷却；定时任务走同一更新入口。`accepted/pending/partial/blocked/failed` 区分任务受理、缓存读取与错误；`recent-window` 不被标为全史完成。                                   | 新来源须把认证失败、账号验证、频控、网络和字段异常映射成可诊断的脱敏状态，不把缓存或任务受理称为取得新文。                                   |
| 正文图片  | 正文只在旧值为空时补入；图片按允许域名、大小和格式受限抓取并内嵌到 SQLite，任一正文图片失败则该次正文记缺失，旧正文保留。                                                                                    | 真实回包确定正文 URL/字段后验证同一文章的正文、图片及重启离线展示。                                                                          |
| 导出      | 现有 Markdown、Obsidian、RSS 与浏览器 ZIP 使用保存内容；ZIP 对正文或附件缺失明确标未完整。                                                                                                                   | 在副本用新来源文章验证附件相对路径、ZIP 解压和 RSS/Markdown/Obsidian 内容；旧库缓存不能算新来源通过。                                        |

规范文章 ID 当前为 `WX_<公众号数字ID>_<mid>_<idx>`，必须从可核验的原文链接取得。`assertProviderPage` 只能保证适配器交付的 ID、链接、公众号和时间**自洽**；它不能单独证明上游字段就是实际发布时间，也不能把 `chapter.updateTime` 转成发布时间。若新来源只给 review ID 或短链，须先取得有证据的身份对应关系，再决定是否扩展契约。

## SQLite 副本演练

- 从当前生产 SQLite **只读**在线备份到本 worktree 的 Git 忽略目录；备份 `integrity_check=ok`，12 个订阅、1447 篇文章。
- 在备份副本生成保护基线，再对副本应用现有 `20260929010000_provider_refresh_cooldown` 迁移。副本 `quick_check=ok`，`provider_refresh_attempt_time` 列存在。
- 新版 `verify-preservation.py` v3 对副本迁移前后比较通过：12/12 订阅、1447/1447 文章，0 条保护违反。它保护订阅名称、封面、简介、状态、创建时间、排序、旧目录/合集绑定，以及文章 ID、号身份、标题、可信发布时间、来源、已核验来源、旧正文、旧图片、创建时间、包括零值的指标；空来源/正文/图片可补。运行状态、同步时间和覆盖状态允许正常变化。保护快照只保存摘要，不读 `accounts`；v1/v2 基线仍可读取，但会明确提示无法覆盖的新字段。
- 本演练只验证**现有迁移与保护工具**，没有新来源导入，更没有生产写库。备份数据库、快照及验证报告均未纳入 Git。

复演时使用 `apps/server/scripts/backup-sqlite.py` 的 `--database` 和 `--backup-root` 参数创建一致性副本，然后在副本执行 `verify-preservation.py snapshot`，只对副本迁移/导入，再执行 `verify-preservation.py verify`。后续真实导入须比对新文章身份、重复更新后的旧字段、图片本地化和导出，且在生产前重新取得备份。

## 依赖真实来源的下一步

1. 先取得目标号至少五篇真实不同文章，并逐条核对公众号、稳定 ID、原文链接或可证明的规范身份、标题及实际发布时间；旧库和 Mock 不计入。
2. 用真实响应定义分页/增量游标、终止条件、去重和检查点提交规则；近期窗口与订阅前全史分开验收。当前 `ProviderPage` 没有游标字段，不能凭端点目录推定其语义。
3. 验证正文与图片后，由总控决定新适配器的显式路由、凭据私有配置及最小数据迁移。随后在 SQLite 副本跑导入、重复更新、旧字段保护、RSS、Markdown、Obsidian、ZIP、重启及第二个号；通过后才考虑单号生产更新。
