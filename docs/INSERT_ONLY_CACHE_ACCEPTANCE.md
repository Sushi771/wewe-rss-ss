# 方案三纯新增路径验收（2026-10-11）

基线 `9b37845c4eb5eff2f5d480cc75cc207f0106a4a8`。本交付为独立临时副本增量补丁，
没有生产写入、迁移、平台请求、登录、/add、图片下载、部署或发布。

## 功能与依赖

接入原 `syncCachedWechat2RssPage` 缓存入口，显式开关默认关闭。事务只 INSERT 真正
不存在的文章，原始 lease 在写前及提交前核验，批次与必要 feed 状态同事务提交。
revision/dirty 均在 COMMIT 后。拒绝、过期、缺表、关闭开关等回退原全备；已证实的
异常身份冲突隔离，不让原前缀匹配漏检造成逻辑重复。覆盖、媒体补写、删除和迁移
保留原保护。风险与恢复流程见 [策略说明](INSERT_ONLY_CACHE_POLICY.md)。

配套周期守卫的独立补丁 SHA-256 为
`afaa7096a12484d2744d44b5718aca41dba6920e7893b1fcb22abd2c952fb9d6`。
本增量不包含守卫、备份脚本或 main.ts，避免重复应用。消费其
`recentVerifiedSqliteSnapshot` / `assertInsertOnlySnapshotPermit` /
`notifySqliteSnapshotDirty` 三接口，原始 lease 对象不会在事务中替换。

服务器构建、TypeScript 与针对修改源码的 ESLint 通过。6 个相关套件 136 项通过：
新增边界、原缓存同步、原备份门禁、来源入口、文章离线下载和图片未完成导出。
包含并发、冲突、半失败、重试、用户后编、旧字段全量保护、失败全备拒绝写入、
提交后通知及未知身份回退。守卫自身的异常套件另由配套窗口验收。

## 实测基准

只读使用现成 SQLite 与本地缓存，源库 626,597,888 字节、14 订阅、1,718 文章，
现成缓存 289 条。选取 5 篇缓存中可核验的身份及旧库可信时间，仅在隔离 seed 移除
这些行来模拟真正不存在的文章；保留其余 1,713 篇。同一 seed、同样 5 篇列表在
旧/快路径各测 6 次。快路径使用最终真实周期 owner，未伪造时间戳许可。

| 耗时项                 | 旧路径 p50 | 旧路径 p95/max |  快路径 p50 | 快路径 p95/max |
| ---------------------- | ---------: | -------------: | ----------: | -------------: |
| 原入口完整保存         |   8.465 秒 |      10.516 秒 |    1.816 秒 |       2.099 秒 |
| ORM 事务（含内部校验） |   1.775 秒 |       1.918 秒 |    1.672 秒 |       1.969 秒 |
| 每批完整备份           |   6.486 秒 |       8.474 秒 |           0 |              0 |
| 只读许可查询           |          0 |              0 |  4.125 毫秒 |     5.176 毫秒 |
| 事务内 lease 断言合计  |          0 |              0 | 18.679 毫秒 |    29.953 毫秒 |
| 提交后 dirty 通知      |          0 |              0 |  4.314 毫秒 |     5.569 毫秒 |

启动完整快照独立记录：p50 9.219 秒，p95/max 10.139 秒。启动备份、复制、迁移准备
及保护核对不计入保存延迟。lease 断言已属于事务耗时，不能重复相加。收益主要是
省去逐批全备，ORM 并未变成零耗时；有限样本 p95 等于最慢样本，不是生产 SLA。

每组验证实际新增 5、更新 0；旧文章所有列及其他表一致；重复投递新增/更新均 0，
revision 不变；列表不宣称正文完成。旧路径各执行 1 次全备，快路径各 0 次逐批全备。
实际通过 SHA/integrity 验证的完整快照已恢复到另一隔离目标，旧行及其他表指纹一致。
网络请求数 0。详细分段见 [公开数值记录](INSERT_ONLY_CACHE_BENCHMARK.json)。

联测曾因旧复制版本比较 Python/Node 的 Windows 设备号而拒绝许可，最终周期补丁
已分别证明各自稳定文件身份。成功数字来自最终交付版本，没有绕过身份断言。
两个 Prisma 延迟事务同时升级锁曾触发引擎 panic，快路径复用原同机 PID 文件锁，
双客户端回归通过；它没有扩成全库写屏障。

## 复现与父集成边界

干净基线上先应用配套守卫，再应用本增量，按项目文档安装依赖及生成 Prisma 客户端。
保持开关关闭，先在隔离数据库迁移和回归。已有库迁移必须执行原完整写前备份；新
schema 必须有对应成功快照。父任务统一决定生产启用，本窗口没有代替上线验收。

基准从 `apps/server` 运行，明确传入只读输入与可写工作目录：

```powershell
node -r ts-node/register/transpile-only -r tsconfig-paths/register `
  scripts/benchmark-insert-only-cache.cjs `
  "--source-db=$sourceDb" "--cache-db=$cacheDb" `
  "--work-root=$workRoot" --samples=6 --batch-size=5
```

复制、schema 准备、模拟缺行和恢复仅在新工作子目录发生。脚本保留验证快照，约需
10 GB 临时空间；输入路径、原始元数据、数据库及完整日志不得提交。这是现成缓存的
保存演练，没有取得新平台文章或正文。

关闭策略不会撤销正确数据。后续编辑过的新文章不能按批次粗暴删除，本交付没有该
撤销工具。整体恢复可能丢最近成功快照后的新增/编辑，需保留当前库并核验后再决定。
