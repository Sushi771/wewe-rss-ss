# 自动刷新缓存差量入口与本地续接（2026-10-12）

## 用户行为

上海时间 09:15、14:00、17:30 的正常定时保持。每个新轮次动态取得全部启用、来源合资格的订阅；不是只刷新某几个固定公众号。关闭页面后由后台执行，保留串行提交、30 秒队列节流、15 分钟单号冷却和持久请求回执。

自动及手动批次的缓存阶段统一使用 `syncCachedWechat2RssPage`。已有完整文章直接跳过；无变化不创建文章事务、写前备份、插入账本或重复文章。纯新增仍须通过原周期快照内存租约守卫；守卫过期、异常或条件不符时回退完整写前备份保存，未延长原租约及事务上限。

已记录为缺正文且没有后续修改的行可以安全补缺。自动路径不会重写已有正文，不下载媒体；用户有意清空或存在后续修改的内容保留，并显示剩余正文缺口。媒体待补不等于正文或上游更新完成。正文补齐和来源补齐保留文章 ID、可信发布时间、标题和笔记，更新检查使用原值条件保护并发修改。

本号本地缓存/保存错误仅将该项记为失败，其他号继续；10 次缓存未就绪检查耗尽同样仅结束本号检查。鉴权、风控、账号异常、未知上游回执及无法分类的上游错误继续暂停整轮，不自动重发或绕过安全限制。

## 明确的 cache-only 恢复

内部 `resumeRefreshCacheOnly(batchId)` 续接原批次已经受理的项。持久 `cacheOnly` 模式只读本地 `WECHAT2RSS_CACHE_DB` 的一致性 SQLite 快照；不调用 `/add`、`/addurl`、HTTP 缓存接口、原文接口、媒体下载或共享下载消费者。Windows 传输使用 ASCII JSON，中文及 emoji 无损，原时区必须可信。

未受理项保留 `queued`、`accepted=false`，不能因本地遍历被记作上游更新完成。原普通 resume 不能将 cache-only 批次恢复为提交模式。cache-only 结束后，新的正常授权定时轮次仍覆盖当前合资格订阅；不补发过期轮次。

本地维护应先核验新鲜一致性完整备份并在副本演练，停掉精确确认的本机服务，再使用固定产物的 `server/cache-recovery.cjs` 入口。本入口没有 HTTP 路由或自动 bootstrap。恢复完成后启动同一固定产物；回退只换程序，使用当前数据库，不能恢复旧库丢弃新增或编辑。

## 实现与验证

预检仅取得元数据及 SQLite 计算的小型缺失标记，避免传输/解析旧大正文。保护保存候选限定公众号范围，并新增 `articles_mp_id_idx` 索引。副本 `EXPLAIN QUERY PLAN` 从 `SCAN articles` 变为按该索引 `SEARCH`。准备、候选查询、写入及事务总耗时分别记录；不把这项优化宣称为原超时的唯一根因。

离线回归覆盖真实 `runManualRefresh(..., cache, automatic=true)` 自动入口完整 14 号轮次、21 篇不变跳过、新增及安全补缺、单号失败隔离、重复投递无写、正文清空保护、cache-only 重启/重复恢复零提交、全局安全停止及快照异常回退。SQLite 缓存 reader 独立验证只读、同号唯一名称、中文/emoji、时区。

新鲜生产副本及冻结现存缓存完整 14 号重放保持 1719 篇、HTTP 请求为 0、无变化重跑不产生新备份。旧身份仅用经核实的同公众号、全局唯一字符串 `o_id` 证据单独补来源，不通过标题/时间猜测合并，不迁移 ID。原始缓存、数据库、凭据、笔记和私有诊断不上传。

本地首次广泛回归在同时构建/备份/回放时出现超时，未据此宣称全部通过；受影响 8 套 89 项离线回归已通过。最终 GitHub 两套 CI、生产运行产物、当地安全续接及未完成媒体的结果以发布核验报告为准。没有进行真实平台测试采集或小红书浏览器自动化。
