# Main WeChat runtime extraction

Source: `aeb7483c85db8d13f1345011266ae7ee6046adc0`. Direct prerequisite: PR54 at `389bd33ae2ea8eee4d0d1231c8634562836531cd`, based on main `7f392f85865491d685f14fb16e5f0b27286374ac`. This change extracts the WeChat refresh path instead of merging the integration branch.

## Included behavior

| Boundary                      | Implementation and reason                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Explicit upstream refresh     | `TrpcService.beginManualRefreshAll`, prepared refresh claims, validated response receipts and the persistent batch worker retain the deployed submission, deduplication, restriction and recovery rules. A completed request with an interrupted acknowledgement remains unknown; observation and cache recovery do not resubmit it.                                                 |
| Ordinary cache writes         | Only `CollectionService.collectWechat2RssRecent` and its three avatar helpers move from the deployed collection service. They use the original incremental admission, actual transaction durability checks, identity/CAS checks, SQL receipts and atomic merges. A full snapshot budget is independent of admission for these writes.                                                |
| Existing unknown occupancy    | The original release-binding and explicit disposition handlers retain approval/evidence hashes, instance/source binding and quiescence checks. Releasing old occupancy never invents an upstream success.                                                                                                                                                                            |
| Scheduling and cache arrival  | The deployed Shanghai schedule, persistent round intent and local cache watcher use the same batch/cache functions. Existing opt-in flags, enabled feed selection and night restrictions remain required.                                                                                                                                                                            |
| Article list                  | Narrow identity pagination, current-page metadata/body presence, bounded revision-aware reuse and optional timing are carried together. The same authenticated transport sends list pages independently of slower batch procedures. In-flight next-page requests share work; failed reads require an explicit retry. Loaded pages and position survive rereads and page restoration. |
| High-risk deletion            | Feed/article deletion keeps a new verified pre-action recovery copy, target identity recheck, writer admission and an atomic delete. Ordinary incremental writes do not replace this protection.                                                                                                                                                                                     |
| Backup and write coordination | The deployed coordinator, backup root/global budget and periodic snapshot owner are retained. The change does not alter cadence, retention approval or copy limits. Startup status and write gates remain compatible with the deployed audit protocol.                                                                                                                               |

The generic subscription task/batch storage and their guarded status/recovery RPCs are dependencies of the deployed worker. They retain their existing distinctions between accepted, waiting, blocked and unknown. The original main add dialog handles a pending result without claiming success or dereferencing a missing feed.

## Scope limits

Native login remains the main implementation. Other collection methods, owner/search/import/replay behavior, the native body-retry handler and export handlers retain their main implementations. The old export attachment path remains `attachments/`; its regression still verifies the actual image bytes and absence of a remote dependency. This is not parity with every feature in the deployed integration branch.

No XHS service/router/provider, Rnote or paid prototype is registered. The seven historical migrations and dormant compatibility tables remain the PR54 schema contract. Management-group UI and the integration branch's larger reader/download/archival workflows are not introduced.

The independent daily-backup lifecycle (PR55) and the later exact saved-media writeback are excluded. There is no new media mutation, local-resource manifest setting, lifecycle flag, three-plus-one policy, automatic retirement entry point or deployment action here. Optional history-review/retirement tooling is not activated by this application slice; its helpers do not authorize maintenance.

The existing main release launcher retains its synchronous inspection flow. Its narrow changes qualify the existing WeChat scheduling settings and use the deployed single SQLite connection URL. It packages the required local cache and snapshot Python scripts. Startup-worker modules are preserved as dependencies of the owned startup/audit regression; this change does not activate the integration branch's desktop or background-start release workflow.

## Evidence and reproducibility

`scripts/main-wechat-runtime-scope.test.cjs` checks a committed manifest of source hashes: every unrelated collection member remains main, the four selected members remain deployed code, native login remains main, and critical claim/write/backup/list policies retain their exact deployed blobs. It also checks application registration and exclusions. The serial-worker rollback fixture is the exact 52,746-byte source from `f82fadeba752cffbc8934010c0bd05dc35b88675`, with a SHA-256 assertion; CI needs no unrelated branch checkout to exercise old persisted state.

The regression set uses owned synthetic SQLite databases and local fixtures only. It covers abruptly killed transactions/remote claims, late commit acknowledgement, duplicate callers, source changes, finite backup budgets, restart recovery, terminal coverage, explicit old-occupancy release and protected deletion. UI checks execute the actual refresh component and its progress component. The authenticated HTTP browser fixture covers held statistics, rapid next clicks, selection, two-page restoration, rereading both loaded pages, group/search/date intersection, one failed request and explicit recovery.

The first local browser attempt could not connect to its own Chrome debug port under the sandbox (`EACCES`); a native Windows run was required. That run found an unnamed checkbox in the old main list. After adding its accessible name, the complete browser scenario passed. These are synthetic regression results, not a measurement of production latency or new production acceptance.

The workflow uses Node 24 for the owned `node:sqlite` startup/compatibility tests, matching the verified local runtime. No local dependency installation is required. The existing image-import preservation job remains enabled. Exact commit CI and independent review are required before merging; PR54's green CI and the source release's natural-refresh acceptance do not validate this new tree.
