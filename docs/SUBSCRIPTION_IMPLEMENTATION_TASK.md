## 3. 对现有设计的明确修正

### 不锁死 /api/query

保留 SubscriptionProvider 和独立 Wechat2RssProvider，但接口选择服从真实数据是否够用，而不是 JSON 比 RSS 更优。

优先取得同一合法私有实例、同一目标号的最小真实响应，对照 /api/query 与 /feed/:id.json、/feed/:id.xml。谁能可靠提供稳定文章身份、原文链接、时间和正文，谁承担文章输入；可以让 JSON Feed／RSS 成为主输入，/api/query 用于已存文章查询或补充。这是同一 Provider 的内部选择，不是切回其他来源。

官方示例未列字段不等于真实接口一定没有字段，但也不能自行编造。不要按标题＋时间、数组位置或猜测的 ID 拼接跨接口条目。先沿用现有经核验的文章身份与旧短链映射；任何新身份映射必须证明稳定、无歧义、不会与旧库重复。不能确认身份的记录不进入生产。

若没有真实实例，可按已公开合同做最小实现、解析器和明确标记的模拟测试；未知字段保持待验，禁止用假样本宣称上游适配已通过。真实来源已证明不可行时，不继续开发大量仅服务于该候选的功能。

### 分开近期订阅与完整历史

第一交付目标是恢复近期文章订阅、后续更新及本地归档，不是重新下载旧库，也不是证明上游拥有所有历史。

Wechat2RSS 官方说明只抓最新 20 篇、只收录群发消息。/api/query 的日期查询针对上游已保存的文章；不能把 before/after 当成无限历史分页。上游未收录的更早历史和非群发文章必须列为明确的能力缺口，不能悄悄标成已完成。

对已存在的日期范围测试历史查询即可；新实例没有更早条目不应单独否决日常订阅。日期粒度和边界按文档及实测核对，使用有界重叠查询与稳定 ID 去重，不能直接把最后一条的日期作为安全翻页游标。

部署时考虑 RSS_KEEP_OLD_COUNT=-1 保留上游以后已取得的文章；本地库不因上游窗口缩短而删除旧文章。这项配置不能补出从未抓取的历史。长期停机或更新间隔过长造成的窗口缺口要明确报告，不能承诺绝对不漏篇。

### 账号状态、任务受理、同步结果分开

/login/list 可用不代表文章可取。/add/:id 会提交异步更新任务，不代表已取得最新文章。

新订阅可通过 /addurl 或 /add 添加；已有号的主动更新仅在受控频率下触发一次。定时同步优先读取上游已有结果，不把所有读取都变成 /add 请求；同号手动、批量和定时任务要合并去重、互斥，不能叠加轮询。

根据真实证据区分 pending、blocked、partial、成功读取缓存和成功归档；无法证明上游任务已完成时保持待更新状态。保存最后尝试、最后成功和文章覆盖信息，失败不推进成功检查点。频控或认证异常使用有界退避，不无限重试。

## 4. 连续实施顺序

先检查现有工程、来源实现、部署条件和私有配置是否具备，只检查必要字段的存在与有效性，不回显秘密。优先复用现有代码，避免重复建设已有 Provider 或导出逻辑。

若有合法可用的私有实例，优先以一个目标号验证真实输出，再按实测字段完成适配。若缺授权、实例或本人扫码，尽早集中说明缺项，同时继续完成所有不依赖这些条件的最小可验证工作：

- Provider 合同、注册／显式路由、私有配置和默认关闭开关。
- 上游客户端、格式解析、身份与日期校验、错误分类、测试夹具。
- 现有添加、单号／全部更新、定时入口的接线；保留原有导出，不激活旧来源。
- 最少必要的 pending／blocked／partial 界面提示、真实联调脚本。
- 使用官方镜像的隔离部署配置、独立持久卷、备份和回滚准备；锁定已核实版本或 digest，不猜镜像名。
- SQLite 副本测试、构建、类型检查、回归与 GitHub CI。

不要将缺少一个账号授权扩大成“所有代码都不能做”；也不要在没有真实数据的情况下把候选适配大规模做完后宣称成功。完成不受阻的工作后，只剩外部条件才停。

授权邮箱、激活码、RSS_TOKEN、Cookie 均由本人在本机私有配置中填写，不要求粘贴到聊天。扫码和人工验证由本人完成。一次列清本轮真正需要我做的动作及完成后如何续接，不反复问能否继续写代码。

Wechat2RSS 当前公开授权限制个人学习研究，并禁止商用和内容分发；不得直接扩展成公司系统或公开服务。发现实际用途不符时，单独说明所需授权，不代购、不规避限制。

只在已授权机器内部署，默认仅本机／明确私网可达；未授权不开放公网，不替换其他项目容器、不修改全局代理、系统证书或 Defender。

## 5. 联调、数据保护和验收

目标号优先“妈妈部落畅聊阁”，再验证第二个已有号；之后逐号覆盖接手时全部订阅。每号记清成功、受阻及文章覆盖范围。

先在隔离环境验证目标最近至少 5 篇真实不同文章的来源身份、链接、发布时间和正文，选择确有图片的文章验证图片落盘及离线展示。不能用旧库或公开演示号代替目标号验收；公开样本只能验证格式。

在 SQLite 一致性副本上验证真实导入、原 ID 对齐、重复更新、重启和导出。上游数据未变时重复更新新增为 0；若上游确有新文，应按真实增量导入，不能为了测试固定断言 0。

旧的非空正文／图片／有效指标不被缺失字段覆盖。身份冲突阻断受影响批次，不以模糊匹配强行合并。正文或图片暂时失败需标明不完整、提供有界重试，不能删除旧数据或让一个号阻断其他号。

写生产前验证一致性备份能够恢复、确认实际数据库与产物路径；单号事务写入，小范围切换后逐步扩展，不重建库。默认不改 schema；确有必要时只做可回滚的加性迁移并说明原因，不能为遵守“不改表”而制造错误映射。

清洗正文，限制网络请求目标、重定向、大小和超时，防止不可信 HTML／图片访问本机敏感地址。API Token、授权信息和会话不进入 Git、日志、浏览器、文章和导出；不要将图片代理 HMAC 参数与 RSS_TOKEN 混为一谈。

验收包含：文章链接添加、单号更新、更新全部、真实定时任务触发与重启后恢复、正文／图片、本地按号批量导出及全部原订阅结果。RSS／JSON Feed 输入正常不代表原来的 Markdown／Obsidian 导出自然正确，必须实际打开文件检查。

“定时运行过”“重复读取成功”和“捕获到一次上游后来新增文章”分别记录。没有自然出现新文章时，可交付已实现、已部署及已验证部分，但持续新文增量仍标为待验证；不伪造发布、不高频等待、不把未发生的外部事件写成验收通过。

## 6. 自动接续与上下文控制

我授权后续窗口继承本任务，在尚有可执行工作时自动继续，无需每阶段征询是否继续。

先检查当前环境实际提供的主任务创建／续接工具。存在且支持该操作时，完成一个有意义单元或上下文接近容量前，保存提交和精简交接，创建一个接手当前项目的后继主任务；核对其任务 ID、工作目录、实际 gpt-6-sol / xhigh 设置及启动状态，不把创建记录当作已开始工作。交接后旧窗口不再并发写同一 checkout。

新任务只加载当前任务书、精简交接和相关代码，不携带整个旧聊天／全部日志。新任务继续继承同样的接续、数据保护和验收要求，直到产品完成、我明确停止，或只剩必须由我处理的外部条件。

没有创建新主任务工具时，不编造工具、参数或新窗口链接，不把子代理冒充新主窗口。可在现有工具能力内继续、使用上下文压缩或有限子代理；子代理只承担明确独立的小任务，不递归派生、不并发写同一文件。仍无法继续时，保存准确交接，并给出一条新窗口续接指令。

不能用自动接续绕过平台限额、权限审批或费用边界。只剩缺授权、扫码、上游受限等外部阻塞时，不创建空转窗口，不反复审计同一报告，不无依据重跑失败协议。没有新信息、代码变化或验证进展的循环应停止。
