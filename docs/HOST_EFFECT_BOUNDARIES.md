# Host release effects and observation boundary

`reference-inspection` and unknown claim kinds have no host write or controller capability. This is a cooperative host-tooling boundary, not a sandbox for arbitrary JavaScript or a replacement for operating-system permissions. Ordinary startup outside a release scope keeps its existing behavior. The frozen approved application package is not rebuilt by this host-tooling repair.

## Common enforcement

`lib.cjs` supplies `hostEffects.fs` and `hostEffects.processes`. Every host module uses these gateways instead of capturing native mutators. Filesystem functions are read-only only when explicitly classified; other functions, writable open flags, Promise mutations and file-handle mutations check the current writer capability before dispatch. Child-process dispatch, including custom `util.promisify` handlers, checks before execution. Dispatch looks up the current implementation, preserving the existing offline preloader and controlled test hooks. Workers, third-party builders, dependency adapters and SQLite recovery also have entry checks because their effects can bypass the JavaScript filesystem gateway.

The gateway reads the already-loaded adjacent `release-scope` lease without loading a policy or opening a new lease. A standalone packaged runtime with no release-scope module remains self-contained. The registry implementation alone uses native writes for its bounded lock/ledger/sentinel protocol; an observation lease therefore still changes control metadata. A physically read-only baseline uses `scope-inventory.cjs --inspect`, not `open`/`within`.

Within **any** scope, synchronous/asynchronous verification disables receipt reuse and receipt publication. `readActiveRelease`, `checkedRelease`, `verifyRelease`, `verifyReleaseAsync` and compact `verifyRunningRelease` perform the complete byte audit without creating or repairing `.verification-cache`. Existing receipts are neither trusted as a substitute nor modified. Identity-tool cache misses keep using the existing read-only fallback. RSS acceptance writes only to the operation's identity-owned reserved audit.

`installDesktop` rejects every active release scope before asset resolution, helper compilation or native dispatch: desktop shortcuts are not registered output of this release protocol. An explicitly approved standalone shortcut installation remains a separate owner action. This repair never invokes it on a real desktop.

Python/PowerShell/VBS entry scripts do not acquire JavaScript observation capability. Host invocation is blocked at the common process gateway unless it is the explicit pinned read-only query path. Direct standalone registration, desktop launch, migration/recovery or cleanup is a separate owner action; these scripts are not imported or executed to establish a baseline. In particular, neither `register-logon-task.ps1` nor a desktop shortcut writer is part of read-only discovery.

## Evidence and limits

Regressions include the independent ordinary/nested/equal-size pointer counterexamples; real no-output cached read, async verification and compact read cases; stubbed desktop installation before native dispatch; sync/callback/Promise/file-handle/process gateways; custom promisify/offline-hook preservation; and indirect builder, dependency, Worker, browser and recovery entries. Successful unscoped tests still validate normal startup, receipts, dependency closure, synthetic SQLite and owned cleanup.

These tests create no production database or real desktop shortcut and perform no production registry adoption, scan, native query, restart or deletion. Source pins, complete real roots/baseline, role disposition, finite capacity policy and independent operational acceptance still precede production use.
