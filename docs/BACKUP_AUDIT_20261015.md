# wewe-rss-ss 日常操作整库备份只读审查

审查日期：2026-10-15。结论基于既有 Git 对象和源码，不是生产性能实测。未打开生产数据库、未复制数据库、未执行真实备份、未启动应用、未发送订阅/正文/图片请求、未安装依赖、未改生产或他人工作区。

## 版本与结论

| 标记            | 精确版本                                   | 本报告含义                                       |
| --------------- | ------------------------------------------ | ------------------------------------------------ |
| B／线上         | `be1a5d03c92b9a4497c1ff226f9440099f5fc360` | 用户给定的运行版本；以下未注明版本的行号都指 B   |
| R39／已修未上线 | `d3f4af046accbd2453bf403691338c9592f938c6` | 普通 Wechat2RSS 增量刷新、启动审计及订阅删除候选 |
| R42／已修未上线 | `fe1ae55b71f5888744bb1f79ee4937881ae9a36b` | 基于 B，仅已有分组改名去逐次全备及相应 UI 优化   |

**确认的主要问题：**

1. 分组新增、改名、拖动、排序都显式在事务前等待整库备份。R42 只修已有分组改名，新增/移动/排序仍需修。
2. `recordCollectionResult` 为了写很小的 running/failed 回执而全备；部分来源内部再次备份。外层已写 running，内层不能复用刚做的快照。
3. 一波最多 5 个更新请求，先逐号串行备份并写冷却预留，全部准备完成才并发发送；不是一次全备保护整波。
4. 30 秒复用不是“30 秒最多备份一次”：任何实际提交会使下次失效；WAL/journal 存在时 B 直接不复用。高频小写因此仍可能逐次产生大文件。
5. Prisma 钩子不自动发起全备，但会让所有写入以及保守处理的 raw SQL/事务等待别人的全备，扩大感知延迟。
6. R39 去除的是普通 **Wechat2RSS** 刷新链，不能宣称所有来源、所有写操作已改。单篇补抓、其他来源、订阅添加/接续、小红书日常操作仍留有门禁。
7. 反向缺口同样存在：B 的订阅单删/批删、单篇文章删除没有独立全备；R39 补了前两者，文章删除仍未覆盖。不能把高风险保护一起拿掉。

源码链接统一指精确提交，例如 [B 的分组实现](https://github.com/Sushi771/wewe-rss-ss/blob/be1a5d03c92b9a4497c1ff226f9440099f5fc360/apps/server/src/collection/xiaohongshu.service.ts#L144)、[B 的通用采集包装](https://github.com/Sushi771/wewe-rss-ss/blob/be1a5d03c92b9a4497c1ff226f9440099f5fc360/apps/server/src/trpc/trpc.service.ts#L1410)、[R39 增量路径](https://github.com/Sushi771/wewe-rss-ss/blob/d3f4af046accbd2453bf403691338c9592f938c6/apps/server/src/trpc/trpc.service.ts#L1114)、[R42 改名](https://github.com/Sushi771/wewe-rss-ss/blob/fe1ae55b71f5888744bb1f79ee4937881ae9a36b/apps/server/src/collection/xiaohongshu.service.ts#L150)。下文 `路径:行号` 与版本标记可直接复现定位。

## 请求、复用、新建、阻断的真实关系

应用全备主链：业务 `await createVerifiedSqliteBackup()` → `sqlite-backup.ts:243` 的 `sqliteWrites.snapshot` → `sqlite-backup-reuse.ts:67` 判断复用 → 不满足时 `sqlite-backup.ts:123` 启动 Python → `backup-sqlite.py:98` 同库操作系统锁 → `:139` 新 UUID 目录 → `:170` SQLite 在线全量复制 → `:176` 全库 integrity_check → `:185` 整文件 SHA256 → `verification.json`。

| 层                                    | 会新建整库文件吗                                                                                               | 等待/失败的影响                                                                                                        |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 业务调用 `createVerifiedSqliteBackup` | 这是“请求保护”；可能复用，不能将调用次数直接写成新文件数                                                       | 调用方 await，失败通常不执行后续写入/外部提交                                                                          |
| B 的 30 秒进程内复用                  | 源文件身份、大小、纳秒 mtime/ctime、100 字节头均不变；无 WAL/journal；备份文件身份不变且未过期，才返回已有回执 | 仍先取得全局 snapshot 独占准入；排队时间不会因最终复用而消失。实际写入通常使下一次需新建                               |
| 真正 Python 新建                      | 每次新 UUID 目录+整库文件；不是表级或 SQL 日志                                                                 | 源连接在复制后释放，但应用独占准入一直保持到校验、哈希及子进程返回结束                                                 |
| PrismaService 钩子                    | **不新建**。`prisma.service.ts:14–38` 包装事务及非 ORM 只读操作                                                | `sqlite-write-coordinator.ts:33–74` 排队。普通 ORM find/count 可继续；raw 查询和只读事务保守排队。其他页面的小写也会等 |
| `protectedProcedure`                  | **不新建**。`trpc.service.ts:149` 是鉴权/启动写禁用检查                                                        | 启动审计未通过时阻止 mutation，不是每个 protected RPC 自动全备                                                         |
| 周期 owner 查询/lease/dirty           | **不新建**。`sqlite-snapshot-guard.ts:230,304`                                                                 | 查询忙/过期会使 B 的快新增回退到原全备；dirty 只安排后续周期，不立刻全备                                               |

B 的协调队列最多 256 项、单项等待 75 秒（coordinator:20–21）。Python 默认总预算 55 秒，复制预算默认/上限 **45 秒**（backup-sqlite.py:98–116），Node 子进程超时 60 秒（sqlite-backup.ts:186–188）；退出未确认继续 fence 后续写入（:160–180）。旧 `SQLITE_BACKUP_COORDINATION.md` 的“15秒”已落后于 B 源码，不能作为线上限时保证。这些是上限/失败路径，不是实测时长。

R39 的 protected 全备复用机制另有变化：Node 不再采用 B 的 30 秒头部缓存（R39 sqlite-backup.ts:252–261）；Python `backup-sqlite.py:205–254` 对已有 protected 文件重算哈希、完整性、全部 schema 和逐列 typed rows，证明一致才 `reused:true`。所以“没有新复制”也可能全库扫描并持有门禁。R39 普通刷新绕开此路径；尚未迁出的日常入口仍会承担这些成本。不要为降低延迟放宽高风险快照的证明。

## 是否有隐藏循环、逐条重复、整批等待

**没有发现“备份函数调用自身”的无限递归。** coordinator:101–104 明确拒绝在已经开始的write/transaction里申请snapshot，避免自锁；同一事务内多条SQL复用write许可，不会每SQL新建快照。

**有重复链条和持续重试放大：**

- 其他来源普通刷新：外层backup → committed running → 内层backup → 保存 → final；两层备份中间的状态写已经改变源。B复用不可能跨过这次提交。外层不需为running制造恢复点，最终状态与正文事务共提交即可。
- 缓存页变化：engine先 sync(listOnly)，再 syncText，后媒体sync；这些是不同阶段/事务，不能当作一个请求只备份一次。B全备次数由真正需要写的阶段决定，不按每张图计算。
- `cache-sync-engine.ts:288–310` 对正文/图片仍缺失或保存异常保留job，每60秒再试，没有单job次数上限；每次若仍落到原protected saver就再次请求全备。这是后台循环，不是每次1秒tick必备份。media安全停止、夜间规则、no-op预检查可阻止部分路径。R39把该Wechat2RSS写链迁出全备，保留重试语义即可。
- cache monitor明确不监听SHM（cache-sqlite-monitor.ts:99–103），避免读标记造成自触发扫描；监听DB/WAL＋只读指纹，没有“自己备份文件一变就再备份”的调用链。
- 新增订阅接续task每30秒醒，单任务最多10次/5分钟（subscription-tasks.ts:306/328/355）；每个可保存identity/metadata阶段仍可能全备。刷新准备安全失败补试手动最多3次、自动最多8次/24小时，并指数退避（batches:1905–1926）；备份失败也可能消耗该预算后再次触发。未知已发请求没有因此自动重发权限。
- 一波5条更新先逐条prepare，最后并发发送；因此确认是**逐号重复且整波发出前等待**。传统整号刷新、批量添加则worker串行，用户先拿到任务回执不等于后台已完成。
- 分组移动与排序一次RPC内多成员/多SQL只有一个备份请求；不能把事务内循环误报成每成员全备。多次拖放形成多个RPC才多次保护。
- tasks.snapshot / batches.snapshot / singleTasks.snapshot / wechat2RssAddReceipt.snapshot 只复制JSON回执到已有backup目录：分别 subscription-tasks:230、batches:996、single-tasks:400、add-receipt:25–29。**它们不是再次复制整库**，也不递归创建DB快照；不过在大批历史回执时仍有文件IO成本。

## 优先级与最小修复建议

| 优先级           | 具体范围                                                               | 最小改动与不可丢失的保护                                                                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P0 安全边界      | 订阅单删/批删、单篇删除、直达迁移入口                                  | 采用R39已补的订阅独立protected delete；文章删除补同等边界；直接迁移命令要求受控保护入口。不能以删除成功回执代替恢复点。不要因解决性能而削弱升级/迁移/删除                                  |

| P1 尚未覆盖高频  | 新建分组、移动、排序；小红书新增/启停；单篇正文补空；订阅头像/名字接续 | 分别复用原锁/CAS/FK/去重和incrementalWrite，在一个SQL事务原子提交结果。先只读验证明显no-op/无效输入，事务内再复核。无必要新UI、新队列或新备份体系                                          |
| P1 通用包装      | owner/public-album/history及不可用来源回执                             | 拆开“是否调用来源”和“如何事务保存最终状态”；普通增量不因running/failed/blocked回执要求全备。来源变更、历史合并、人工纠错另设独立保护，不全局删除recordCollectionResult里的备份后就宣布安全 |

普通增量的SQL回执可以证明哪些ID/字段被原子提交、消除重复执行，也能防远端提交重放；**不能在数据库损坏或被删除后恢复旧正文**。因此它替代普通逐次快照而不替代周期恢复点及高风险操作的独立快照。现有导出文件回执则继续以文件原子发布承担自己的恢复责任。
