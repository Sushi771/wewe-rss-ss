# 缓存目录事件与批量入库性能验收

本增量基于 `ff150609305ae21ecaaac8cf41deb8e3f0e025ab` 加已交付的缓存快同步补丁。先应用原补丁，再应用本增量；保持 `feed.cacheRevision`、`feed.cacheSyncStatus` 的输入与输出合同。现有刷新入口、Provider、正文图片队列、夜间限制和旧数据保护继续复用。

## 产品行为与边界

明确配置本地 `WECHAT2RSS_CACHE_DB` 时，Node 监听数据库所在目录的主库、WAL 文件事件，20ms 内合并重复提示并唤醒原 Python 监测进程。忽略 SHM：只读连接本身可能修改读标记，监听它会形成自触发全文扫描循环。Windows 文件名比较按文件系统大小写规则处理。目录监听能跨越主库文件替换；监听关闭或报错后重建。不可用时保留每秒轮询校准，不新增 100ms 全文轮询。

提示仅触发只读、已提交的一致 SQLite 快照。正文、图片等字段形成的内容指纹变化后才通知快同步工作器。未提交修改、单纯 metadata/checkpoint、重复通知不能直接增加 revision。提示早于提交、丢失提示及服务重启仍由后续事件与轮询复核。Windows 保持短只读连接，避免长期文件句柄阻止主库替换。监督进程关闭 stdin 后提示监测器退出，避免留下孤立监测进程。

100ms 是本机提交后发现的优化目标，不是保证，也不等于入库完成。快照仍需读取和计算缓存内容指纹；缓存规模、磁盘负载、Python/Node 调度、事务与一致性备份都会增加耗时。忙碌工作器收到新信号后接着再运行；已有读取预算、延迟补全和退避保持不变。远程或仅 `/list` metadata 的 5s 路径不受文件事件加速。

## 技术变更与保护

- 原预检中的已保存文章身份按快照归一化一次，避免每篇重复遍历、解析相同 URL。
- 仅 `cachedPage` 路径在原写事务内每最多 40 篇共用候选查询；保留稳定 ID、两个原文 URL、跨公众号冲突及标题/时间的旧身份隔离检查。列表阶段候选读取不加载旧正文；正文阶段继续使用原非空补全。
- 仍在任何写入前执行原一致性备份及完整验证，不修改 SQLite durability、ACL 或凭据设置。未引入跨批次备份复用；其他写入路径尚无共同排他边界，不能把较旧备份冒充当前批次的恢复点。
- 不变缓存不写库、不增加 revision，也不额外备份。正文、图片、有效时间、指标及私人笔记不能被空值覆盖。发生身份冲突时事务回滚。
- 统一整合的副本演练发现，不明身份旧记录与候选同标题/时间时会安全跳过，但预检原先仍将该候选当作待新增，导致重复读取时再次完整备份。现在预检与写事务复用同一旧身份判断：全批仅含已存/隔离记录时零写入、零备份；混合批仍在原写事务重查并保留隔离诊断。真实身份及非空保护没有放宽。

## 可复现的离线检查

在已安装项目依赖的 server 目录执行：

```powershell
pnpm test --runInBand --runTestsByPath src/feeds/cache-sqlite-monitor.spec.ts src/feeds/cache-sync-engine.spec.ts src/feeds/cache-sync-storage.spec.ts src/trpc/wechat2rss-preflight.spec.ts src/collection/wechat2rss-list-metadata.spec.ts
python scripts/test-watch-wechat2rss-cache.py
node -r ts-node/register/transpile-only -r tsconfig-paths/register scripts/benchmark-cache-signals.cjs
pnpm build
```

Jest 覆盖目录事件过滤/合并/重建、忙碌工作器信号续跑、81 篇分块查询、旧不明身份隔离、冲突回滚、非空字段保护及不变缓存无备份/revision。Python 覆盖提交前提示、重复提示、漏提示、stdin 关闭、WAL/checkpoint、同尺寸补全、主库替换和夜间边界。

合成基准使用临时 SQLite：14 个合成订阅、每号 93 行、每行约 4KiB 正文。逐次记录 WAL、主库提交的发现耗时，并测试提交前通知、主库替换、故意漏提示、监听重建、仅 metadata 与 checkpoint 无重复通知。输出完整样本与 nearest-rank p50/p95/max；空闲 Node CPU/RSS 只代表监测调用方，不能冒充 Python 或全服务负载。全部 fixture 不读取生产配置、公众号缓存或图片，不请求上游。

现存缓存导入比较使用另行保存的私有隔离快照：相同计时钩子、交替原版/增量顺序、多轮各批次完整保留，分别记录提交→发现、发现→列表保存、备份、ORM 与余项；核验旧记录全部字段及其他私人表，并恢复代表备份。私有路径、号名、文章内容、笔记、凭据及运行证据不入本公开文档或 Git。

## 验收解读

本机并发负载下的最终合成事件测试，WAL 与主库提交各 10 个样本：WAL 发现 p50/p95/max 为 144.8/278.9/278.9ms；主库为 135.9/306.7/306.7ms。100ms 未达标。提交前提示不提前报告，替换/漏提示/监听重建分别为 116.0/395.1/128.8ms，metadata 与 checkpoint 未增加内容通知。2.2s 空闲窗口 Node CPU 93ms、RSS 约 89.6MiB；这包括 TypeScript 测试运行器，不代表生产构建或 Python 负载。不同负载应重新测量，不能承诺上述最大值。

Mock、合成提交和旧缓存补录只能证明对应工程路径。不能称为真实上游自动更新恢复，也不能证明新正文或新图片下载成功。图片完成、前端可见与完整端到端实时更新在本轮范围外。当前结果和达标与否见交付附带的脱敏统计；未达 100ms 或未降低入库耗时必须原样报告，不用最好一轮替代 p95/max。

本窗口仅制作独立临时副本的增量补丁和验收材料；生产部署、共享树整合、GitHub 推送和 CI 由统一集成窗口完成。

备份瓶颈核对：每个真正写入批次仍只启动一次 Python、执行一次 SQLite 在线备份、一次完整性检查及一次 SHA-256。没有可删除的重复全量哈希。此前同条件六样本中，备份 p50/p95/max 为 12870/24220/24220ms，发现至列表入库为 15042/29197/29197ms，ORM 为 2129/5280/5280ms。跨号共享恢复点需要覆盖其他写入口的共同排他边界，属于后续架构工作；本轮不缓存较旧备份、不降低 SQLite 耐久，也不把不同负载的早期样本作直接速度对比。
