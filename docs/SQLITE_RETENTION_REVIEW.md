# SQLite recovery-point maintenance

Ordinary incremental refresh uses transactions and durable receipts, with no full snapshot per item or round. See [incremental refresh safety](INCREMENTAL_REFRESH_SAFETY.md). Timed backups keep their current interval. High-risk operations retain an independent verified backup. Single and bulk feed deletion use the same protected backup gate and one cascading transaction; see the linked safety document for concurrency and identity checks. This replaces the earlier 15-minute shared-round recovery design; that design is removed from the implementation.

## Finite budgets and business impact

Production recovery generation defaults remain 32 GiB, 48 copies and 4 GiB free physical space. Declared legacy roots count toward the same budget; aliases are deduplicated and cycles rejected. This PR does not expand global limits, change production configuration, remove a real backup or deploy anything. Full recovery quotas can prevent the next timed/high-risk backup and produce an alert, but do not stop ordinary refresh or routine startup. Actual source-volume shortage still blocks a write safely.

The default planner reads recovery metadata and bounded file content, without requesting platform data or modifying subscriptions, articles, images, metrics or groups. Planning and validation never delete, move, archive or restore a database. The optional scanner runs after server listen, fails independently, and defaults off. Registered scanner reports alone rotate to at most three files of 256 KiB each; unknown files and approval documents are never automatically collected. The separate explicit periodic executor below is never called by that scanner or by a backup attempt.

## Explicit opt-in retention policy

Without `SQLITE_RETENTION_POLICY`, unique historical points remain held for human review. An explicit JSON policy enables a bounded selection proposal, not deletion. Defaults are targets of 48 ordinary points (`maxOrdinaryCopies`) and 32 GiB (`maxOrdinaryBytes`), latest two, minimum one hour, one point per two-hour bucket over the recent 24 hours, daily coverage for seven days, weekly coverage for four weeks, and a maximum ordinary age of 28 days. The legacy `roundDays=7` field applies only to old producer-marked write-before points; current ordinary refresh creates none. Mandatory recovery windows and active references take priority over both targets, producing an alert if they exceed either. Retention targets do not expand the independent generation hard caps or change write admission.

Only same-source, structurally valid producer-marked ordinary periodic/write-before receipts are eligible. Unknown/unmarked legacy files remain held. Current owner/latest references, newest same-source recovery, explicit protected paths, deployment/migration/identity/manual boundary names and high-risk `recoveryOrigin.kind=protected` receipts are always protected. A high-risk backup may reuse only another verified protected point with fully equal schema and typed rows; it cannot silently borrow an ordinary periodic point that rotation might retire.

A `retention-protected.json` manifest uses format `sqlite-retention-protected-v1` and an explicit `paths` array (at most 256) within declared roots. `SQLITE_RETENTION_PROTECTED_PATHS` also accepts an explicit JSON path array. Source data must remain outside all recovery roots. Newly written high-risk verification receipts contain the protected producer marker; old boundaries must be identified conservatively during release review.

Warnings cover byte/count pressure, mandatory windows exceeding target, physical headroom, reserve-copy threshold and projected retention headroom. Projection uses a configurable expected generations/day value, not a claim about measured production growth. Check the actual periodic interval when selecting it: for example a 15-minute interval generates up to 96 points/day. Warnings never authorize deleting unique history or blocking all subscriptions.

## Read-only planning and action-time validation

Run `python apps/server/scripts/sqlite-retention-plan.py --database <source> --backup-root <root>` from an isolated maintenance context. It reads at most 64 MiB in ten seconds by default and bounds entries/directories; insufficient proof is held or rejected. The server opt-in uses `SQLITE_RETENTION_SCAN_ENABLED=1` and an interval from 3600 to 86400 seconds, default 3600. The script, backup helper and resource query helper can also be inspected/run independently without deploying the server.

Every proposed exact batch binds paths, file identity, actual hashes, representative recovery point, root/reference inventory and policy digest. Before a separately authorized irreversible action, validation requires an exact approval no older than five minutes and a successful empty Windows Restart Manager resource report no older than 60 seconds. Unique expired history additionally requires explicit `uniqueHistoryPaths` approval. Replaced files, new owner/protection references, changed policy/inventory, sidecars, active ownership, resource query failure or changed hashes reject the action. Validation rechecks the retained representative with SQLite quick_check and never performs the deletion itself.

Do not turn a validated list into recursive directory deletion or wire the planner to a timer that deletes files. Any real deletion/move/recycle action still needs an exact current list, independent recovery review and the user's specific authorization. Development build/dependency/cache directories are outside this database planner; no broad cleanup command is provided.

## Explicit bounded periodic rotation (Windows)

The existing tool now offers `--periodic-only` preview and a separate `--execute-periodic` action. An explicit `SQLITE_RETENTION_POLICY` is required. This mode counts all recognized same-source periodic points, including protected ones, against the count and byte targets. It retains current owner/latest references, at least the latest two periodic recovery points, configured time representatives and all other protections. Only older producer-marked `periodic-snapshot-<UTC>-<id>` directories immediately under this managed root can enter its batch. Necessary upgrade/migration/protected backups, old write-before points, foreign sources, legacy roots, unmarked files and historical article data are excluded. An extra sibling, SQLite sidecar or link holds the point. If recovery obligations exceed capacity, the tool warns and preserves them; it cannot promise a target is achievable by deletion.

Preview with placeholders referring only to the intended managed root:

```text
python apps/server/scripts/sqlite-retention-plan.py --database <active-db> --backup-root <managed-root> --periodic-only
```

Review the exact generated `.retention-review/retention-<time>-<digest>.json` locally. No database is deleted. The approval must be newly confirmed for this actual list, not inferred from an earlier broad cleanup authorization. It contains `batchId`, `digest`, `approvedAtEpoch`, `action: "rotate-exact-periodic-backups"`, and exact arrays `paths` (database files), `metadataPaths` (their verification receipts), `directories` (their generation directories) and `uniqueHistoryPaths` (every selected historical state). Removing an old unique point loses that recovery state even while the current database and retained recovery points remain intact; confirmation must acknowledge this. Do not publish these local paths or approval documents.

Use the existing `query-retention-resources.ps1 -Batch <batch> -Output <new-resource-report>` for this bounded batch. Run the same tool with `--batch <batch> --approval <approval> --resources <report>` to validate only. **Only after the user specifically authorizes this exact real deletion**, add `--execute-periodic`. The same current policy must be supplied. Approval lasts five minutes, the bound resource report 60 seconds, and changed inventory/references/policy/identity/hash invalidate the batch. The executor refuses generic review batches and does not support non-Windows deletion.

The executor shares the existing source snapshot OS lock and exclusive `.space-budget.lock` with recovery generation. It opens ancestor directories and every selected database/receipt, generation directory and retained representative with Windows handles, verifies file identity, hashes and single-link status before the first irreversible action, and denies concurrent selected-file access/rename. Deletion uses `SetFileInformationByHandle(FileDispositionInfo)` on the verified handle; there is no pathname unlink fallback or recursive deletion. Receipts are removed only from the approved list, and generation directories only when empty. This bounds both snapshot bytes and their owned metadata after successful rotation. See Microsoft's [handle deletion contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle) and [file sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

### Protection publication and execution share a critical section

Independent review of the first rotation patch found that directory handles do **not** prevent a new protection file from being created after validation. That patch must not be treated as integration approved. Repeating a hash or adding a directory-change notification would still leave a check/action race.

Execution now requires `retention-protected.json` to exist before preview in **every** declared reference root, including legacy roots. It must accurately contain the current manual protections; the executor never creates an empty placeholder or replaces an operator's manifest. Its existing identity/content record is bound into the preview. Execution pins these files with read sharing only before final validation and retains those pins through the last action: a preexisting writer makes acquisition fail; a write, truncation, rename or atomic replacement during execution fails at the native file-sharing boundary. A protection published before the pins instead invalidates the old batch. Existing owner/latest and protected receipt files are also pinned against modification while remaining readable for validation.

The current source backup publisher writes its latest reference under `.full-snapshot-<source>.lock`; the current guard holds `.snapshot-<source>.lock` for its lifetime, including unchanged-owner renewal and publication after copying. Execution must acquire **both** existing OS locks and pins their actual files against unlink/rename, along with the relevant ancestor directories. Thus those publishers cannot start or publish a missing owner/latest file during execution. A running guard causes rotation to refuse; the tool does not stop it or the service. This restriction applies to the maintenance invocation, without changing ordinary subscription write admission.

This is a current-producer, single-source protocol, not an OS-wide directory mutation barrier. Only the current source's fixed owner/latest names are supported publishers; existing legacy refresh-owner names, other source references or unknown publisher names hold execution. Manual protections must use the pinned manifest, not ad-hoc owner/latest JSON files. Independent tools that bypass these publication contracts, or an older producer whose locking is unproved, are outside the executable scope: do not execute rotation in that environment or erase references/change configuration to force admission. Preview remains available. The code does not claim that arbitrary privileged filesystem writers are excluded. A new `referenceConcurrency` plan binding rejects old rotation approvals; obtain a fresh preview and exact authorization after these conditions are established.

The batch is not a filesystem transaction. A failure after some deletions returns `partial-failed`, completed objects and attempted objects with an uncertain-outcome flag, then stops; there is no automatic retry or recovery action. A changed inventory prevents replaying that old batch. Save the local result and prepare a new preview/confirmation for any later action. A crash can leave the small generation lease as an explicit hold; it must not be erased to force a retry. Successful execution removes only its own unchanged control lease. No production rotation, schedule or configuration is enabled by this development change.

Known separate release-tool limitation: the independently reviewed authority-file replacement window remains unresolved. This change neither invokes publishing/deployment nor repairs or expands that tool; it is not evidence that the release authority boundary is fixed.

## Recycle-bin limitation

Windows exposes recycling through IFileOperation, but undo is conditional and may be held only for the Explorer session. `SHQueryRecycleBinW` reports current size/count, not a guarantee that a particular large file can be restored. Recycling has not been implemented or demonstrated as a recoverable retirement action here, and is not counted as freed physical space. No recycle, restore or empty-bin operation is part of this PR.

References: [operation flags](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags), [recycle-bin query](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shqueryrecyclebinw), [aborted-operation check](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-getanyoperationsaborted).

## Verification and rollout boundary

Python tests cover finite tiers on tiny SQLite fixtures, protected high-risk receipts, exact unique-history approval, changed references/policy, bounded scanning, junction deduplication/cycles, active users and unchanged business bytes. TypeScript tests cover scanner isolation and periodic failure alerts. Native startup tests cover full quota with zero recovery copies, schema and integrity validation; backup tests retain pre-write refusal on exhausted budgets.

The release owner must review the exact CI-passing SHA against the then-current production commit, reconcile actual recovery inventory and protect upgrade/migration boundaries before any controlled release. This PR is development-only. It does not authorize merging main, force pushing, deployment, restarting services, global configuration changes or irreversible cleanup.
